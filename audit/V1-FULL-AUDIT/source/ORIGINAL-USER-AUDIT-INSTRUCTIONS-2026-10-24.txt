# 第一部分：自主执行授权

## 1.1 自主执行模式

用户已授权你在本次审计范围内：

1. 自主调查项目现状。
2. 自主制定审计任务和执行顺序。
3. 自主拆分模块与子任务。
4. 自主选择审计方法和工具。
5. 自主执行安全的本地静态分析、构建及测试。
6. 自主收集日志、截图与验证证据。
7. 自主整理问题及审计结论。
8. 自主制定整改计划。
9. 自主维护审计进度与恢复检查点。
10. 自动进入下一项尚未完成的审计任务。

在上述范围内，不需要逐阶段向用户请求批准。

不要频繁询问：

- 是否开始？
- 是否继续？
- 是否进入下一阶段？
- 是否执行下一轮检查？
- 是否生成报告？

只要任务安全且具备执行条件，就直接推进。

## 1.2 授权边界

本次以审计为主，原则上不修改现有业务代码。

允许：

- 新建独立审计目录。
- 编写独立测试脚本。
- 使用隔离测试数据库和测试漫画副本。
- 创建审计文档、测试日志和问题报告。
- 执行可安全运行的本地检查。
- 在项目允许的范围内启动和测试软件。

未经用户另行授权，不得：

- 删除或覆盖真实用户数据。
- 执行破坏性数据库迁移。
- 大规模重构或替换业务代码。
- 删除 Git 历史或强制重置仓库。
- 强制推送、自动合并或发布。
- 上传包含源代码、私有漫画或密钥的资料到第三方服务。
- 进行产生费用的真实 API 压力测试。
- 修改用户全局系统环境或安装高风险系统组件。

必要时使用沙箱、临时目录或文件副本。

若某项测试存在不可控风险，记录 BLOCKED 并继续其他工作。

**用户不在电脑前，不代表获得了不可逆操作的授权。**

# 第二部分：Plus 额度优化和模型分工

## 2.1 基本原则

本项目使用 ChatGPT Plus，模型额度有限。

在保证审计质量的前提下，优先节约高级推理额度。

采用以下推荐分工：

### Luna：默认执行模型

承担约 60%～70% 的执行性任务，包括：

- 项目文件与目录盘点。
- 代码数量、文件类型和依赖统计。
- 静态检查工具运行。
- TypeScript 类型检查。
- Python 静态检查。
- 构建与编译。
- 单元测试、集成测试及回归测试执行。
- UI 页面、组件及路由盘点。
- 测试日志、截图和证据整理。
- 功能覆盖矩阵初步建立。
- 明确、局部、低风险缺陷的分析。
- 审计文档和报告初稿整理。

### Sol Medium：深度审计模型

承担复杂推理与关键裁决，包括：

- 系统架构分析。
- React/Tauri/Python 跨模块接口。
- 数据库事务和数据完整性。
- OCR、SFX 复杂分类逻辑。
- 上下文翻译和状态机。
- 图片消除、排版及导出。
- UI/UX 深层交互问题。
- 并发、异常恢复和资源管理。
- 高风险缺陷根因分析。
- 审计证据复核。
- 整改优先级及最终发布判断。

### Sol High：默认禁用

不主动使用 Sol High。

遇到 Sol Medium 无法可靠判断的重大问题：

1. 保留已有证据。
2. 标记 HIGH_REVIEW_CANDIDATE。
3. 说明需要升级的原因。
4. 继续其他可执行审计。

本次审计不依赖 High 才能结束。

## 2.2 模型调用限制

不得假设当前运行环境可以自动切换模型。

如果具备真实的模型分派能力，则按上述规则分配。

如果不能自动切换：

- 使用当前可用模型推进。
- 将需要更强推理的任务独立记录。
- 不因无法切换模型而暂停全部审计。
- 不得虚构其他模型已经执行了审查。

无需主动使用 multi-agent-project-orchestrator，也不依赖其他 Agent 才能完成本轮审计。

## 2.3 节省额度的执行策略

必须遵循：

1. 本地工具优先于 AI 人工逐行分析。
2. 使用索引、搜索和依赖关系定位代码。
3. 每个模块保留已审计文件范围及证据。
4. 不重复读取已经审查且未变化的文件。
5. 代码未变化时复用有效测试证据。
6. 长日志保存到文件，报告仅保留关键摘要与证据链接。
7. 按模块分批执行，避免一次性读取整个仓库。
8. 核心业务逻辑优先进行深度审查。
9. 对低风险辅助代码采用自动化检查和抽样复核。
10. 不为了节省额度降低验收标准。

自动化扫描必须覆盖全部有效源码；人工深度审阅根据风险确定范围。

第三方依赖、构建产物、缓存、模型权重等不得当作自研源码逐文件审阅，但需要检查相关依赖、安全及运行风险。

# 第三部分：审计基线与防中断机制

## 3.1 首先建立审计基线

审计开始前，检查：

- Git HEAD Commit。
- 当前分支。
- 工作区未提交修改。
- 项目目录结构。
- 当前软件版本。
- 实际技术架构。
- 构建环境。
- 依赖与锁文件。
- 现有测试体系。
- 已有功能与开发文档。
- 已知历史阻断和证据缺失。

不允许随意切换、清理或覆盖用户现有工作区。

审计针对明确记录的代码版本进行。

若项目仍有未提交修改，应将其作为基线的一部分记录，并标记由此产生的复现限制。

此前历史验收证据缺失的问题必须保留原状态。

新的 V1 审计证据可以建立新基线，但不得将缺失的历史证据自动改为 PASS。

## 3.2 建立独立审计目录

目录：

`G:\CODEX\New Manga\audit\V1-FULL-AUDIT`

创建必要的子目录：

- `reports/`
- `evidence/`
- `logs/`
- `tests/`
- `screenshots/`
- `checkpoints/`
- `handoff/`

使用清晰、稳定的文件命名。

避免在审计目录之外制造不必要文件。

## 3.3 持久化进度

建立以下核心状态文件：

`AUDIT_STATUS.md`

`AUDIT_PLAN.md`

`AUDIT_TASKS.md`

`AUDIT_EVIDENCE_INDEX.md`

`AUDIT_ISSUES.md`

`AUDIT_RESUME.md`

其中 `AUDIT_RESUME.md` 必须记录：

- 当前审计阶段。
- 已完成任务。
- 未完成任务。
- 最近验证结果。
- 已发现的关键问题。
- 最新代码版本。
- 下一个可执行任务。
- 恢复运行所需命令。
- 阻断与风险说明。

每完成一个独立审计任务，更新状态。

## 3.4 断电与中断恢复

假设运行过程可能出现：

- 电脑关闭。
- Codex 会话结束。
- 模型额度不足。
- 工具调用中断。
- 测试进程异常退出。
- 上下文窗口不足。

所有审计阶段都必须可以从持久化检查点恢复。

恢复时：

1. 读取 AUDIT_RESUME.md。
2. 核对 Git 和审计基线是否变化。
3. 核查上次执行结果。
4. 识别尚未完成的任务。
5. 从最后一个可信检查点继续。

不得因会话重启而无意义地重新开展全部审计。

若当前平台无法跨会话自动运行，应保存完整恢复入口，不得虚称已经设置后台任务。

# 第五部分：测试与证据标准

## 5.1 审计结果分类

每个检查项必须标记为：

- PASS：有充分证据证明满足验收标准。
- FAIL：已证实存在缺陷。
- BLOCKED：受明确外部条件阻断。
- NOT_TESTED：尚未执行验证。
- NOT_APPLICABLE：经过核实不适用。

禁止默认 PASS。

## 5.2 问题严重程度

P0：数据破坏、严重安全问题、核心流程整体失效。

P1：重要功能不可用、严重稳定性问题、重大业务错误。

P2：一般功能问题、较明显的交互或性能缺陷。

P3：低风险维护性、局部体验与代码优化问题。

每个问题建立唯一 ID：

`NM-AUD-0001`

问题必须记录：

- 严重等级。
- 问题分类。
- 文件路径和定位。
- 复现条件。
- 预期与实际结果。
- 证据文件。
- 影响范围。
- 根因或待核实假设。
- 推荐修复方案。
- 对应回归测试。
- 当前状态。

潜在风险不得直接写成已证实 Bug。

## 5.3 证据真实性

严禁：

- 没有运行就写测试通过。
- 没有截图就声称界面验收通过。
- 没有检查文件就声称文件已审查。
- 将 Mock 通过当作真实 API 通过。
- 将开发环境通过当作安装包通过。
- 将历史 PASS 当作本轮 PASS。
- 将无法复现的问题随意判定不存在。

所有结论应当可以通过保存的证据重新核验。

# 第六部分：审计执行策略

## 6.1 阶段顺序

执行顺序：

P0：基线、项目盘点、审计任务 DAG。

P1：工具化全量静态扫描与构建检查。

P2：架构、接口、数据库和核心业务深度审计。

P3：OCR、SFX、翻译、修复和导出专项审计。

P4：UI/UX 与真实软件运行测试。

P5：性能、安全、稳定性及 Windows 交付审计。

P6：综合端到端测试及需求覆盖核对。

P7：问题去重、分级、根因分析和整改规划。

P8：最终交叉核验与 Release Gate。

允许并行执行相互独立且不会争用关键资源的任务。

不允许跳过某阶段却宣称其已完成。

## 6.2 自主循环

每轮执行：

PLAN → INSPECT → EXECUTE → VERIFY → RECORD → UPDATE → NEXT

其中：

PLAN：确定当前可执行任务。

INSPECT：定位文件、依赖和实际实现。

EXECUTE：执行审计、工具扫描或测试。

VERIFY：验证发现和测试结果是否可靠。

RECORD：保存问题及证据。

UPDATE：更新审计状态与完成范围。

NEXT：自动选择下一项任务。

禁止只完成 PLAN 就停止。

## 6.3 遇到困难时的处理

遇到问题优先尝试：

1. 重新定位准确文件。
2. 检查环境与依赖。
3. 使用替代性静态验证。
4. 将任务拆小。
5. 使用隔离副本复现。
6. 执行不依赖该阻断的其他任务。
7. 记录证据缺口。
8. 制定后续补验方案。

不得在同一失败命令上无限重试。

连续重复失败应登记阻断，切换任务。

## 6.4 无人值守要求

用户可能不在电脑前。

不要因正常阶段切换而等待确认。

若遇到需要用户独有凭据、付费权限、高风险系统变更或不可逆操作的情况：

- 不得自行越权。
- 登记外部依赖。
- 继续其他安全任务。
- 最终汇总需用户介入的事项。

如果所有剩余任务都无法安全执行，则保存最终恢复状态并如实结束当前运行。

不把工作停止解释为审计已全部通过。
