## 关键技术点

1. **任务书要求的「先清 `media_artifacts.current_revision_id`」在本 schema 下不可能**：两个 `*_current_not_clearable` 触发器对「非 NULL → NULL」直接 ABORT。正确路径是承认 schema 的意图——复合 FK 声明为 `DEFERRABLE INITIALLY DEFERRED`，**同一事务内两侧同删**即天然破环；探针 E1（拒绝原文）/E3（仅删 revisions 失败，因 deferred 指针在 COMMIT 时被检查）/E4（逆序全量提交成功）把这条链钉死。若 Reviewer 认为必须字面执行该步骤，则只能改 Schema（本 Task 禁止）。
2. **自引用不阻碍多行删除**：`artifact_revisions.source_artifact_revision_id` 是 immediate FK，但在**同一语句**中删除自引用链（rev1 ← rev2）实测成功（E3/E4）——早先看到的失败是 deferred 的 `current_revision_id` 指针，不是自引用。
3. **跨页 provenance（超出任务书枚举的一种形态）**：另一页的 revision 若 `source_artifact_revision_id` 指向被清 revision，则删除会因 immediate FK 失败（E5 实测）。实现选择**先清悬空 provenance 指针**（内容、文件、哈希都不动），从而"永久删除"不会因这一形态而永久失败；被拒的替代方案是硬失败（永久删除无法完成）或 `PRAGMA foreign_keys=OFF`（明文禁止）。对应用例 `test_purge_clears_cross_page_provenance_instead_of_failing`。
4. **无 FK 的残留行**：`pipeline_stage_states` 以 `(target_type, target_id)` 为键且**没有** FK，purge 现在同时清理 page 目标与 region 目标；`page-key-tables-scan.txt` 确认再无其它此类表（`pipeline_*` 的 `region_id` 列无 FK，但由同一页的 `page_id` 一并删除）。
5. **F-7 的"ledger 是指数而非唯一真源"**：`deleted_at` 就是批次身份（同批次共享一个时间戳），所以 `list_batches()` = manifest 批次 + 未在 manifest 中出现的仓库分组（重建批次的 id 为确定性的 `rebuilt:<chapter_id>:<deleted_at>`）。这同时兑现了"读侧容错不得使整功能失效"与 docstring 的 "rebuildable"。
6. **F-10 的拆分**：`existing_source_hashes` 过滤软删（修掉"重导被跳过但章节里没有页"）；`max_source_order` **不过滤**——软删页的 `source_order` 槽位必须保留，否则新导入的页会与将来 restore 回来的页拿到同一个 order。见「待裁定」①。
