## AC 逐条

### AC ①（根因与方案）——达成

根因：`assemble_services` 在启动（GUI）线程 `open_database` 建唯一 `conn`；`SqlitePipelineStore`/`SqliteTargetCatalog`/`SqliteSnapshotProvider` 全部持该连接；`RunController` 的 worker 线程执行 `execute_run`，首个 `_persist` 即 `sqlite3.ProgrammingError`，被 `_Worker.execute` 的 `except Exception` 吞成 `runCrashed`（`commandError` 无 QML 消费者，TASK-052 处理可见化）⇒ 用户完全静默且 run 停留 `running`。

方案：**`check_same_thread=False`（解除 Python 侧线程绑定）+ 四层并发控制论证**（全文见 `connection.py` 模块 docstring）：

1. **CPython `sqlite3` 以 serialized 模式编译**（`sqlite3.threadsafety == 3`）：同一连接跨线程在语句级由模块内部互斥保护；
2. **每 run 单写线程**：`RunController.start` 对并发 run raise ⇒ 任意时刻最多一个 worker 发出 pipeline 写（`put`/`commit_step`）；
3. **SQLite 层串行化兜底**：`journal_mode=WAL` + `busy_timeout=5000`（`_apply_pragmas`）——主线程偶发写与 worker 写事务以 WAL 读不阻塞写、写锁 5s 重试预算交接，不产生 `database is locked` 竞争失败；
4. **已知有界交错**：两线程语句共享连接的单事务 ⇒ 主线程 commit 可能落在 worker `with conn:` 块内、发布一个批次中间快照；每次 `put` 是整 run 的 DELETE+INSERT 全量重放、下一 `_persist` 边界即自愈，最坏=瞬时部分行集，FK/WAL 保证库不损坏。

负向用例：`test_worker_run_and_main_thread_access_coexist`——worker 跑真 run 的同时主线程持续对同一连接读 **和写**（连续 `create_book` + 查询），断言两路写均落盘、run 终态、无异常。

### AC ②（端到端不复现 + 修前判别）——达成

探针 `verification/TASK-048/thread_probe_pre.py`（同一脚本、同一解释器，树由参数切换）：

| 树 | run1 | run2 |
|---|---|---|
| 修前 `c9a7a1e`（默认 64 线程绑定） | `OUTCOME=crashed \| error=SQLite objects created in a thread can only be used in that same thread...` | 同左 |
| 修后（`check_same_thread=False`） | `OUTCOME=finished \| status=completed_with_failures` | 同左 |

`completed_with_failures` = 无 ready provider 时每 step `PROVIDER_UNAVAILABLE` 失败语义的**终态**（AC② "含失败语义"），run 不再崩溃、不再停留 `running`。证据：`thread-pre-fix-run{1,2}.txt`、`thread-post-fix-run{1,2}.txt`。
