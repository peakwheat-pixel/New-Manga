## 3. 四项核心说明（Review 重点）

### 3.1 持久化（survive restart）

provider/network profiles 存 `data_root/settings/` 下两份 JSON
（`provider_profiles.json`、`network_profiles.json`），与
`reading_progress.json` / `export_history.json` 同属 **JSON-backed 中间态**
（store Protocol 明文把 SQLite adapter 留给后续协调切片，T3.1.1 统一存储时
一并迁移）。文件含 `version` 域；损坏文件抛 typed
`ProfileFileFormatError`（fail-closed，不静默清空）；写入原子。两个 store
的行为语义（add 覆盖 / update 缺失抛 KeyError / delete 缺失 no-op）与
`tests/network/net_helpers.py` 的 in-memory 参照实现一致。

### 3.2 重启恢复

测试以"实例 A 写入 → 全新实例 B 读取"建模进程重启（`test_*_survives_restart`）。
凭据侧：API key / 代理密码写入 Windows Credential Manager（OS 托管，天然跨
重启）；profile 仅持 `credential_ref`，重启后经 `has_credential` 恢复
`credential_set` 状态显示。

### 3.3 pipeline 接入（feed the pipeline）

复用 TASK-050 既有通道，**零新增管线代码**：
`SettingsViewModel.saveBinding / saveSettingsSectionJson` →
`PipelineDefaultsService`（application 层唯一写面，含 known-step 校验）→
`pipeline_defaults` 行 → bootstrap 既有 `_load_pipeline_settings` /
`build_provider_runtime(settings=…)` 读取 → run 启动时冻结快照（D06 §49；
run 中修改不静默切换，AC-PROVIDER-003 语义不变）。能力默认绑定
（AC-PROVIDER-002）由 QML 每能力一行直接写入该行。

### 3.4 credential 脱敏（never enter logs/diagnostics）

- API key / 代理密码在 VM 内即刻包成 `SecretValue` 送 vault
  （`WindowsCredentialStore`）；profile/JSON/日志只持 `credential_ref`
  （AC-SEC-001/003）；
- VM 对 QML 只暴露 `credential_set` 布尔；QML 密码框 `echoMode: Password`、
  无回显、留空=不修改；
- `failed` / `confirmationRequired` 消息仅由 id 与静态文案拼成，测试
  断言 payload 中的 secret 值不出现在任何错误消息（AC-SEC-002）；
- TLS 默认开启（AC-SEC-004）；关闭必须走 `confirmationRequired` →
  QML 确认 Dialog → 带 `confirm_disable_tls=true` 重提交（AC-SEC-005），
  测试验证了未确认时不落盘。

## 5. 重要发现：QML context property 初始化竞态（既有，非本任务引入）

实现中观察到：QML 绑定对 context property 的**首次求值**可能早于
wrapper 可解析，随机（≈75%）报 `Cannot read property … of null`；
固定 `PYTHONHASHSEED`、禁用 QML 磁盘缓存均不能消除，属引擎初始化层
（Qt/PySide6 6.11）时序问题。**既有页面同受影响**——master 的
smoke/测试噪音里长期存在 `AppShell.qml / PrimaryNavigationRail.qml …
of null`（T1.1.1 测试输出可见）；SettingsView 因绑定的是数据 model
（失败后无 notify 不重估、页面会空），首次做了系统性防御：

- 所有读取 null-guard；
- `Component.onCompleted`（此时 context 可靠可解析）内以 JS
  `signal.connect()` 命令式接线（绕过 Connections 名称匹配），并调用
  `settingsViewModel.refresh()`（`@Slot`）以 change-signal 驱动全部
  guard 绑定重估。

修复后 smoke 六连跑 SettingsView 相关错误 0（其他页面的既有噪音不在
本任务范围）。**建议 Codex 评估**：既有四页是否在后续 slice 统一采用
同一防御模式。
