## 1. 问题

C-01b 冻结前置③ 要求 AD-002 的「Managed Copy」口径与 AD-003 一致。现状：

| 位置 | 现内容 | 与 AD-003 的关系 |
|---|---|---|
| AD-002 `:4` 哨兵 | `Windows + C#/.NET + Avalonia + Python Core + SQLite + Managed Copy` | AD-003 §2.1 已声明「当前架构哨兵以 AD-003 为准，机械检查同时校验两者」——**可保持不变** |
| AD-002 `:8-11` 横幅 | 已写明「新导入默认引用原文件、不复制不覆盖；既有 Managed Copy 按 AD-003 §3.1 继续读取」 | **已覆盖**新导入语义；但它是**横幅说明**，不是责任表条文 |
| AD-002 `:28` 责任表行 | `Managed Copy｜保持既有实现与验收。` | 冻结时若只读责任表，会读到"保持既有实现与验收"这一**旧默认**表述 |

风险：C-01b 冻结后，若某实现 Task 引用 AD-002 `:28` 作为契约依据，可能被解释为"新导入仍应复制"——与 AD-003 §3.2 冲突。

## 2. 硬约束

1. **AD-003 §7 的字节保留声明**：AD-002 的历史横幅「只追加、未删除或改写任何原有行」已被独立复核**字节级证明为真**（去掉横幅后与变更前 blob SHA-256 完全相同）。若本次改写 `:28` 或 `:4`，该声明即失效，须重新做三口径陈述。
2. **Decision authority: User**：AD-002 的任何正文改动须用户确认。
3. **机械检查**：`tools/governance/check.ps1` 校验 AD-002 与 AD-003 的哨兵字符串（`:261-275` 一带）；改动哨兵需同步检查器，风险高。

## 4. 方案 A 的具体 diff（若选 A）与 D 案说明

**D 案（推荐）**：不改 AD-002 任何字节。解释口径已由 AD-003 §2 表首行「仅取代新导入默认这一范围」+ AD-002 `:9-10` 横幅承载，并在 C-01b 编成 SC-07（旧数据双读）与 SC-01（新导入不复制）；契约冻结直接引用 C-01b 即可。**若选 A 案**，在 AD-002 `:31` 之后追加：

```markdown
> **责任表现行解释（2026-11-01 追加，不修改上表任何原有行）**
> 上表 `Managed Copy｜保持既有实现与验收` 的**现行语义**由 [AD-003](AD-003_REFERENCED_SOURCE_ARCHITECTURE.md) 限定：
> ① 既有 Managed Copy 数据**继续**按既有读取路径工作（**不自动**迁移、**不自动**删除；用户显式盘点后可释放，见 AD-003 §3.1 第 3 条）；
> ② **新导入默认引用原文件，不复制、不覆盖**（AD-003 §3.2）；
> ③ 该行的「验收」仅指旧数据双读与既有验收基线，不构成新导入仍须复制的依据。
> 本段为追加说明；上表原文与 `:4` 哨兵逐字保留（追加不改写任何原有行，§7 ② 继续成立；但 §7 ① 与 §2:28 的「去横幅即原 blob」配方需扩展为「去两段追加区」——见 §4.1）。
```

**不改动**：`:4` 哨兵、`:8-11` 历史横幅、`:28` 责任表行，以及 AD-002 其余全部正文。

### 4.1 A 案的已知代价（FEA-GOV-2 r1 P1-1）

A 案会在 AD-002 `:31` 后新增**第二处**追加区，使 AD-003 已冻结的两句描述失真：`§2:28`「去除横幅…后与原正文一致」与 `§7 ①`「文件已变更——新增顶部状态横幅」只覆盖 `:8-11` 一处。若选 A，必须同步登记「§2:28 复原配方改为去两段追加区」，并按 AD-003 §7 ③ 重做 AD-002 的三口径陈述（需 AD-003 再修订/再 pin）。**这是 D 案更优的原因**。
