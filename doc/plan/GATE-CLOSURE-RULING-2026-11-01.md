## 1. 问题（仍成立）

Gate 的定义文本与被它守门的契约构成**看似的**循环：

| Gate | 定义（原文） | 涉及契约 |
|---|---|---|
| `G-DELETE-CONTRACT` | 「协议字段/码表/**D04-D07** 冻结」（ADJ-001 `:128`；`:10`/`:92` 亦写 D04/D07） | **覆盖 4 个变更包** |
| `G-CONTRACT` | 「**D05** Source/grant/资源契约冻结」（AD-003 §5 `:128`） | D05 |

而**修订前**，C-04b 的条件③要求 `G-DELETE-CONTRACT` 关闭、C-06 的条件③要求 `G-CONTRACT` 关闭（本 v2 已改为「不阻塞」）。

## 2. 事实核查

`D01`–`D08` **不是独立文档**，是 [FEA-00 §13.2](../design/FLUENT_FRONTEND_ARCHITECTURE_PROPOSAL.md) `:762-771` 的**变更包分组**：

| 变更包 | 对应契约（现代载体） | 状态 |
|---|---|---|
| D01 架构补充决策 | C-01b | **已冻结** |
| D02 前端可替换契约 | C-02 | **已冻结** |
| D03 应用端口/错误/capability | C-07 | **已冻结** |
| **D04** 草稿/保护/结果 | **C-08 部分 + 未起草的 draft 契约** | **未冻结** |
| **D05** Source/grant/资源 | **C-06**（推断，见 §3 R-1′ 注） | approved |
| **D06** Run 快照 | **C-08** | **未冻结** |
| **D07** 删除/备份/迁移 | **C-04b**（方案 `:516`/`:770` **明文**） | approved |
| D08 现有任务协调 | 治理文档 | 非契约 |

**关键事实**：`G-DELETE-CONTRACT` 覆盖 **D04–D07 四个包**；C-04b 只承载 **D07**。因此 v1 的"同步关闭"是**只按一个包关闭四个包的 Gate**——错误。

## 3. 裁定

### R-1′ Gate 保持 OPEN，只解除对特定契约的阻塞

**不关闭任何 Gate**。改为修订两个契约的冻结条件③：

- **C-04b 条件③**（原「`G-DELETE-CONTRACT` 关闭」）→
  > ③ `G-DELETE-CONTRACT` 对 C-04b **不再构成阻塞**：C-04b 只承载 **D07**；D04/D06 的承载契约（C-08 及未起草的 draft 契约）未冻结前，**Gate 保持 OPEN**，C-04b 冻结**不改变 Gate 状态**。

- **C-06 条件③**（原「`G-CONTRACT` 关闭」）→
  > ③ `G-CONTRACT` 对 C-06 **不再构成阻塞**：C-06 承载 D05 的**授权面子集**（`SourceAccessRegistry` + source-read grant）；D05 的 lease/重定位·同步/容器页映射/缓存边界由 C-01b、C-09 及后续契约分担，**Gate 保持 OPEN** 直至这些落地。

**理由**：
1. Gate 的语义完整性保护针对**整套删除/Source 语义**；分块冻结单个契约不虚报 Gate 状态，因为 Gate 仍 OPEN。
2. **C-09 不会提前解锁**——C-09 条件②「两 Gate 关闭」在两个 Gate 都 OPEN 时不满足（v1 的错误正在此）。
3. **D04 是删除 preflight 的输入**（PD-01/PD-03 的保护清单依赖草稿/保护语义），先冻消费者后冻被依赖语义是允许的**只要** Gate 仍 OPEN 且 C-09 不动。

**注（D05↔C-06 为推断，非明文）**：方案 `:768` 未点名 C-06；D05 的「必须冻结」含 lease/重定位·同步/容器页映射/缓存边界，C-06 **未全覆盖**。本裁定按"部分映射"处理：C-06 冻结只覆盖其自身 §2 范围，不声称关闭 Gate。**若后续发现 C-06 与 D05 其余部分冲突，走 UNFREEZE**。

### R-2′ M2-C1 扩展：保留独立 Task，顺序改为「释放实现前」

**同批修订 C-04b**（v2 授权，冻结前完成）：

1. **§2.4 的「冻结顺序」句**改为：
   > **冻结顺序**：C-04b 冻结只冻**结构与码表**（§2.3 的 2 码 + §2.4 的 4 个扩展点）。M2-C1 的 §5.11.3 表 + 两个 ErrorView 的**字节修订**由**独立 Task**（不得并入任何删除实现 Task）在**释放任何删除实现之前**完成并复核；复核须含**负向对照**：未扩展 M2-C1 时，新码必须被 host 投影拒绝。

2. **条件⑤**改为：
   > ⑤ M2-C1 §5.11.3 + §5.11.5 的扩展**方案**已冻结在 C-04b §2.4；**字节修订**由独立 Task 在释放删除实现前完成并复核（含负向对照）。

**理由**：
1. **契约层与协议层分离**：C-04b 冻"要加什么"，M2-C1 是字节。
2. **不降低独立性**：v1 写"紧接的实现 Task"是把两件事合并——v2 明确**不得并入实现 Task**，保持独立复核。
3. **安全论证诚实化**（复核 P2-1）：本裁定**不新增运行时保证**。当前 `PermanentlyDeleteBookErrorView` 与两新码在 `apps/**`+`src/**` **0 命中**、host 投影未接线，所以"新码不能用"是**契约纪律**而非机制阻断。因此负向对照必须写进那个独立 Task 的 AC 与 Review。

**适用边界**：R-2′ **仅适用于 C-04b**（复核 P2-5）。C-08 的协议注册若需同类处理，须单独论证。

### R-3 版本批准

**批准** ADJ-001 §6.1 的协议 minor **`2.11`**（新增 `PreviewPermanentDeleteBooks` + 2 码）；**批准** C-06 的 wire **v1.1**（仅新增命令，`ImportPages` 语义不变）。

**兼容性表述**（复核 P2-4）：二者均为 minor，但**兼容性依赖旧端 fail-closed**（ADJ-001 §6.2 `:86` / C-04b §3），**不以"旧端接受新码"为前提**；C-04b 是在**既有** ErrorView 上追加码。

### R-4 C-08 的同构处理（**单独论证**，不自动沿用 R-2′）

C-08 的前置（b）与 C-04b 条件⑤**同构**：都是「新增命令/错误码的协议注册须由独立 Task 完成」。按同口径处理：

1. C-08 冻结只冻**快照结构与 3 个新码的声明**（`RUN_STALE_PREVIEW`/`RUN_PREVIEW_EXPIRED`/`RUN_SNAPSHOT_INCOMPLETE` + `PrepareRun`/`AcceptRun` 的 wire 版本）；
2. **M2-C1 字节修订**（块②：**§5.5 命令表追加 2 行 + 3 码进 §5.5 错误语义与 §8 ErrorEnvelope 允许集合**）由**独立 Task** 在**释放任何 Run 实现前**完成并复核；**wire 版本 = minor `2.12`**（DSH 批准）；两块均为**冻结章节的修订**，须按 M2-C1 自身的修订/复核流程（含版本记录）执行；
3. 复核须含**负向对照**：未扩 M2-C1 时，3 个新码必须被 host 投影拒绝；
4. **与 C-04b 共用同一个独立 Task，但范围是两块、不是一块**（关键修正）：
   - **块①（C-04b，删除章节增量）**：M2-C1 §5.11.3 表追加 2 行 + §5.11.5 的 2 个删除 ErrorView 联合扩展；
   - **块②（C-08，扩展已有 §5.5）**：M2-C1 **§5.5「Run Runtime wire surface（P13-C1，冻结）」**（`:185-226`）的命令表**追加 `PrepareRun`/`AcceptRun` 两行**；3 个 `RUN_*` 码进 **§5.5 的错误语义段 + §8 `ErrorEnvelope` 的允许码集合**（**不是**新增 per-command ErrorView——§5.11.5 的 ErrorView 是删除专属投影，Run 错误走 §8）；wire minor `2.12`。
   - **为什么必须是两块**：M2-C1 §5.11 全章是「项目级作品永久删除」（`:678` 起，protocol 2.10），而 Run wire surface 在**独立的 §5.5**（`:185`，P13-C1 冻结，明写 supersede §5 的 Run proposal 行）；`PrepareRun`/`AcceptRun` 在全文 0 命中，所以是**扩展 §5.5**、错误进 §8，而非「§5.11.3 追加两行」或「新建并行章节」。

**与 R-2′ 的区别**：R-2′ 只适用 C-04b；R-4 需独立成立（P2-1 补 C-08 特有理由）：① C-08 的 `preparedDigest` 是 **canonical JSON 的字节级定义**（键排序/UTF-8/无空白），字节修订必须与算法定义同步，不能只改错误表；② Run 命令面受 **M2-C1 `:125` 的 major 2.0 历史约束**，新命令必须确认为 minor 递增；③ C-08 的 candidate store 是 Host 侧临时存储、**不落 Core DB**，其错误投影与删除线的 DB 事务语义不同。

**Gate 真正的关闭条件**（本裁定明确，不改原文语义）：
- `G-DELETE-CONTRACT` 关闭 = **D04–D07 每包都有冻结契约或经裁定豁免**（D04 → C-08 + draft 契约、D05 → C-06 + 其余、D06 → C-08、D07 → C-04b）。
- `G-CONTRACT` 关闭 = D05 的授权面 + 其余子面均有承载契约。

## 5. 风险与回退

| 风险 | 缓解 |
|---|---|
| 分块冻结被误读为"删除线已就绪" | Gate 保持 OPEN 写进 C-04b/C-06 冻结记录；STATUS 的下一候选不含删除/Source 实现 |
| M2-C1 扩展被无限推迟 | 冻结记录写入"释放删除实现前必须完成"+ 负向对照；C-04b 的 §2.4 已是明文 |
| 负向对照未执行，新码被硬启 | 该独立 Task 的 AC 必须含"未扩 M2-C1 时新码被拒"，独立复核检查 |
| v1 的"投影"结论被误当事实 | 本 v2 已删；Gate 状态真实为 OPEN |
| **共用 M2-C1 修订 Task 耦合**：块①与块②共用 Task 后，一方延期会阻塞另一方 | **两段独立提交**（块①/块②分别 commit + 分别复核）；单一 owner；AC 分包；Task 上限 5 个提交 |

**回退**：若独立复核仍认为分块冻结不安全 → 回退到「先完成 M2-C1 扩展独立 Task → 再冻 C-04b」的严格串行路径。
