# P15-C1-FU1：TestNetworkProfile 目标语义定案

## 来源（**为什么需要**）

P15-CORE-1 Owner（Codex）在实现前**失败关闭**并上报真实缺口，Coordinator 裁决见 [ruling-P15-CORE-1-network-test.md](../../verification/PROJECT-ORCHESTRATION-20261016/ruling-P15-CORE-1-network-test.md)：契约 **§5.2** 的 `TestNetworkProfile` 在 `provider_profile_id` 缺省且 Direct/System 模式下**没有任何探测目标**，而 `status` **只有 `passed | failed`**（L194）且 `failed` 必须有唯一失败阶段（L212）→ **全阶段 `not_run` 时被迫报 `passed`（假阳性）**。

## Acceptance Criteria

- [ ] **AC1 定案目标语义（二选一，Coordinator 建议 A1）**：
      - **A1（建议）**：`TestNetworkProfile { network_profile_id, provider_profile_id }` —— **`provider_profile_id` 改为必需**；目标恒为该 Provider 的 endpoint（经所选 Network Profile 的代理路径）；缺省时按既有规则返回 `INVALID_REQUEST`。
      - **A2**：保留可选并新增第三终态 `status: passed | failed | not_testable`，规定全 `not_run`/`not_applicable` 时必须降级为 `not_testable`（含 `NotRunReason`），并同步 UI 状态矩阵与 §9 投影。
- [ ] **AC2 固化禁止项**（写入契约正文）：**不得**自选公网 URL / loopback / 假目标；**不得**把 Proxy 主机冒充 TLS/HTTP 目标；**不得**用伪造阶段结果满足测试语义。
- [ ] **AC3 六阶段语义闭合**：为每个 Stage 明确"目标从何而来"（Proxy 用 Network Profile 的 proxy endpoint；DNS/TCP/TLS/HTTP/ProviderAuth 用 Provider endpoint 的解析路径），并明确各模式（Direct/System/HTTP/HTTPS/SOCKS5）下每个 Stage 的 `passed|failed|not_run|not_applicable` 判定条件。
- [ ] **AC4 安全与脱敏**：沿用 §5.2 既有约束（结果不得含原始响应/响应体/请求头/认证头/代理凭据/路径/endpoint 的敏感部分）；失败只走 §9 封闭投影。
- [ ] **AC5 兼容与版本**：按 M2-C1 §3.2 声明 minor 递增与向后兼容影响；**不改**其他已冻结语义（G21/G22/G24 与 P10 边界不动）。
- [ ] **AC6 交付**：固定 commit + [Handoff](../templates/HANDOFF.md) + Canonical Evidence（sha256 按**磁盘字节**且**与主仓库一致**——**BL-16/RV-P15-04**；`commit` 列**原样** `git rev-parse HEAD`——**BL-17**；`class` 仅 `CANONICAL`/`SOURCE_PIN`——**BL-19**；`delivery_head` 不自引用——**BL-15**；`status` 合法值、交付用 `in_review`；不得自请审查冒充独立 Review——**BL-18**）。
