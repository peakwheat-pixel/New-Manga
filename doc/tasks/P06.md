## Acceptance Criteria

- [ ] AC1：建立**受控旧版本 runtime**：从协议引入前的 commit 构建旧 sidecar（记录 commit / 构建命令 / 产物 hash），
      并在 `G:/CODEX/New Manga.workspace/` 下建立**隔离迁移根**（不触碰用户数据、主仓与既有 worktree）。
      若无法构建可用的旧版本 runtime（依赖/工具链缺失），必须标 `BLOCKED` 并记录失败证据，不得伪造旧版本。
- [ ] AC2：**全退出迁移验收**（可审计）：以真实进程证明
      (i) 旧版本（或持共享租约的进程）存在时，新版本独占窗口被**非阻塞拒绝**；
      (ii) 旧进程**全部退出（含 kill）**后，新版本独占窗口**首次扫描成功**。
      归档原始 stdout/stderr/exit code/时间戳/进程身份与判别结论，形态对齐 GC-2 的 G3 实测口径。
- [ ] AC3：**旧 catalog 策略逐机确认**：对「已存在但未绑定」的旧 catalog（含含有资源行、以及**旧 schema 缺 lifecycle 表**两种情形），
      以真实运行证据证明新版本行为为 **fail-closed 拒绝启动**（不静默迁移、不复用旧数据），并确认显式迁移只能走另行释放的受控流程。
- [ ] AC4：**出货阻断条件与发布前检查清单**：明确记录「本验收未归档前，发布物不得以启用 sweep 的配置出货」，
      产出可直接被 P20 引用的检查清单（含判定项、所需证据形态、不满足时的处置）。
- [ ] AC5：**不重做 GC2**：不修改 `src/**`、`apps/**`、`packaging/**`、`tests/**` 与 GC-2 已入库测试；
      若发现 GC-2 实现缺陷，**只登记不修**（另立 Task），并在证据中说明。
- [ ] AC6：固定 head 非作者 Review、Coordinator 集成；未完成项必须标 `NOT_RUN` / `BLOCKED`，
      不得用本机单版本口径冒充多版本分发验收通过。

## 依赖、风险与阻塞

- `depends_on`：无硬依赖（`GC2 done` 是事实前提，不是 DAG 边）。P06 不受 AC-DOC Gate 约束。
- 风险一（`BLOCKED` 候选）：**无法构建可用的旧版本 runtime**（历史 commit 的依赖/工具链不可复现）→ AC1 直接 `BLOCKED`，
  不得用伪造或"模拟旧版本"替代真实旧 runtime。此时只交付已得证据与失败原因。
- 风险二：多版本共存场景需要"已装机旧版本"，本仓库不存在该形态；本 Task 只能在**受控构造**下验证机制，
  必须在证据中明确区分「机制验证」与「真实装机迁移验收」，不得混同。
- 风险三：隔离根内的破坏性操作（删除/迁移 catalog）必须限定在构造数据上，且需保留原始证据。
