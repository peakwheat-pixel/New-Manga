## 2. Findings

### P1

#### P1-1 — R-1 会提前关闭 `G-DELETE-CONTRACT`（Gate 覆盖 D04–D07 四个变更包）

- 位置：裁定 §3 R-1（`:40-44`）、§4 影响表（`:71`「ADJ-001 §9 / AD-003 §5 Gate 状态更新为 CLOSED」）、§2 映射表（`:30-34`）。
- 证据链：
  1. ADJ-001 §9 `:128`：`G-DELETE-CONTRACT`（**协议字段/码表/D04-D07 冻结**）——范围是 **D04…D07 四个变更包**；ADJ-001 `:10`、`:92` 亦写「在 **D04/D07** 契约冻结并实施前…」「最终码表由 **D04/D07** 冻结」。
  2. 裁定自己的 §2 表（`:30-33`）：D04 = 「C-08 部分 + **未起草的 draft 契约**」；D06 = 「C-08」；C-04b 只对应 **D07**。
  3. C-08 当前状态 = `approved` r2、**未冻结**（冻结矩阵 `:23` 仍标 pending 条件）；draft 契约**未起草**。
- 影响：
  - 若在 C-04b 冻结时同步把 Gate 标 CLOSED，则 ADJ-001/AD-003 的 Gate 表将**宣称 D04–D07 全部冻结**，而 D04/D06 两包实际未冻——**状态虚报**。
  - 下游 C-09（删除/备份/迁移）条件②「`G-DELETE-CONTRACT` + `G-CONTRACT` 关闭」将**提前满足**，C-09 会在一份**未起草的 draft 契约**（D04 覆盖面）与未冻结的 C-08（D06）之上被冻结——而这正是 Gate 原本要防的顺序问题。
  - D04 的「保护清单/草稿版本」语义是删除 preflight（PD-01/PD-03 的影响清单、保护项）的输入；D07 的删除协议依赖它。**先冻 D07 再冻 D04，等于先冻消费者、后冻被依赖语义**。
- 补充：ADJ-001 `:129` 另有 `G-DELETE-IMPL`（Core 实现 + 故障回归，**OPEN**）——实现侧确实仍有闸门，所以**不存在「立刻就能实现」的运行时风险**；但 Gate 的**状态语义**与**下游冻结顺序**问题依然存在，故仍判 P1。
- 建议（二选一，见 §1 替代路径）：**A. Gate 保持 OPEN，只把 C-04b 条件③改为「Gate 不阻塞」**；**B. 显式重定义 Gate 关闭条件为「D04–D07 各包均有冻结契约或经裁定豁免」并逐包列状态**，D04/D06 落地前不标 CLOSED。

#### P1-2 — R-2 与 C-04b §2.4 的明文「冻结顺序」直接冲突

- 位置：裁定 §3 R-2（`:46-56`）、§5 `:80`（「只更新 Gate **状态值**，不改语义条款」）。
- 证据：
  - C-04b §2.4 `:90`：「新增码**必须同步扩展**两处封闭联合，否则 host 投影会拒绝」；`:99`：「**冻结顺序**：先扩 §5.11.3 表（M2-C1 修订）→ 再扩两个 ErrorView → **最后 C-04b 冻结**。M2-C1 的修订须走独立 Task（不得由本草案直接改其字节）」。
  - C-04b §4 `:112`：「C-04b 须在 `G-DELETE-CONTRACT` 关闭后冻结」。
  - R-2 把 M2-C1 扩展降级为「实现前置」，**允许先冻 C-04b**，并把字节修订交给「**紧接的实现 Task**」。
- 影响：
  - 裁定宣称「不改语义条款」，但 R-2 实质上**反转了 C-04b §2.4 的冻结顺序**，且没有修改该草案字节 → 冻结后 C-04b 文本（§2.4 顺序 + §5 条件⑤）与裁定**自相矛盾**，后续执行者不知道以哪个为准。
  - 「由紧接的实现 Task 承载」与 §2.4「M2-C1 修订须走独立 Task」冲突：若把协议字节修订并入实现 Task，等于**实现者自己定义接口**——这正是 Gate/契约设计要避免的模式。
- 建议（R-2'）：若保留降级，**必须同时**：
  1. 改 C-04b §2.4 的冻结顺序句为「C-04b 冻结只冻结构与码表（新增码在 M2-C1 扩展前不得启用）；M2-C1 §5.11.3 表 + 两个 ErrorView 的封装扩展由**独立 Task** 在**释放任何删除实现之前**完成并复核」；
  2. 把该要求写进 C-04b §5 条件⑤的新文本与冻结记录的强制项；
  3. 保留「M2-C1 修订不得并入实现 Task」的独立性（与 §2.4 原文一致）。

#### P2-1 — R-2 的「机制上无法生效」表述过强（实为当前无实现、靠契约纪律）

- 位置：裁定 §3 R-2 理由③（`:55`「C-04b §2.4 已规定新码未注册前 host 投影会拒绝、§3 规定 `PROTOCOL_VERSION_UNSUPPORTED` fail-closed——不存在『未扩展却生效』的窗口」）、§5 风险表（`:79`）。
- 实证（本 reviewer 实测）：
  - `PermanentlyDeleteBookErrorView`、`BOOK_DELETE_STALE_PREVIEW`、`BOOK_DELETE_PROTECTION_INVENTORY_UNAVAILABLE` 在 `apps/**`、`src/**` 的检索 **0 命中**——host 投影与新码**均未实现**；
  - M2-C1 §5.11.5（`:774-803`）的封闭联合是**契约文本**，不是现行运行时校验；

## 3. 关于「是否为了推进而放宽安全边界」

我的判断是：**动机是解真实的死锁（这一点裁定没说错），但两处放宽超出了「等价替换」的范围**：

- **R-1（可以更安全地表达）**：把「Gate 是投影」作为结论，证据只有 D07 一条明文；D04/D06 的覆盖被「投影」一词**吸收掉了**，没有逐包核对——这是归纳跳跃，不是造假，但结果会让 Gate 状态与 C-09 冻结条件提前满足。
- **R-2（确有顺序反转）**：把「先扩协议→再冻契约」反转成「先冻契约→再扩协议」，并把扩展交给「紧接的实现 Task」——省掉了一个独立前置 Task 的等待，代价是 C-04b §2.4 的冻结顺序条款失效。若保留，必须同步改 §2.4 并守住「独立 Task」。
- 未发现「结论先行、理由凑数」：§2 的事实核查有原文级出处（D07 行、`:516`）；§3 的三层理由中前两层（契约层/协议层分离、ADJ-001 现行语义继续有效）成立，只有第三层（安全不降级）表述过强（P2-1）。
- 未发现**隐蔽**放宽：裁定主动列出回退条件并要求独立复核，过程是透明的。
