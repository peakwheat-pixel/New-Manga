报告 §2 表格声明的顺序为「格式门 → 表查询 → 撤销 → 过期 → containment（canonicalize）→ 读文件」，代码逐行核对**完全一致**：`main.rs`:329–336（取 path/last segment + percent-decode）→ `:337–342`（43 字符 `[A-Za-z0-9_-]` 格式门，**先于**表查询）→ `:344–355`（表查询，未命中 `REF_UNKNOWN_ID`）→ `:356–358`（revoked）→ `:359–361`（expired）→ `:363–366`（`canonicalize`）→ `:367–369`（`ensure_inside_scope` → `REF_OUT_OF_SCOPE`）→ `:370–381`（读文件）。
**`id` 从不参与路径拼接**（只作 `HashMap` 键），因此 traversal 类输入结构性不可达；junction 逃逸靠 resolve 时 `canonicalize` + 前缀包含判定拦截（N-09 实测 `403 REF_OUT_OF_SCOPE`）；若 scope root 本身被替换为 junction，则 canonical target 与字典序 root 不匹配 → 同样 fail-closed。

**已知前置条件（F-02）**：`ensure_inside_scope`（`:246–254`）是**纯字符串前缀比较**，其正确性依赖调用方**先 canonicalize**。请求路径满足该前提（`:363`）；但 `sign_all()` 的 N-05 守卫（`:259–261`）传入的是**未 canonicalize** 的路径，因此该次调用不等价于 resolve 防线——它只证明"一条明显越界的字典序路径被判越界"。我不认为这是可达的 fail-open（N-04/N-09 的请求路径均先 canonicalize），但它使报告 §3.2 N-05 的层级归属失真（见 F-02）。
