## 3. 技术裁定（独立阅读与实验，不引用 Handoff 论证）

1. **`check_same_thread=False` 伴随的并发控制充分**：docstring 的四层论证经逐条实验/实读核实——(a) venv 实测 `sqlite3.threadsafety == 3`，CPython sqlite3 语句级 serialized 成立；(b) `RunController.start` 对并发 run 抛 `RuntimeError`，生产装配中 `WorkbenchViewModel` 单实例持有唯一 controller（viewmodel.py:109），"任意时刻最多一个 worker 写 pipeline"在当前生产形态下成立；(c) `_apply_pragmas` 实有 WAL + busy_timeout=5000，跨线程偶发写交接有 5s 重试预算；(d) "已知有界交错"段落诚实承认了两线程共享单事务、主线程 commit 可落在 worker `with conn:` 块内发布中间快照，且"put 全量 DELETE+INSERT + 下一次 `_persist` 自愈"与 `SqlitePipelineStore.put` 实现和 `ON DELETE CASCADE` schema 完全吻合。**无夸大**，也满足"不得把 `check_same_thread=False` 当唯一措施"的禁令。未发现"database is locked"竞争失败或库损坏路径。
2. **`recover_running_runs()` 接入时序无回归风险**：调用点位于 `MigrationRunner.apply_pending()` 之后；TOO_NEW 库在 `open_database` 返回后即 `raise RuntimeError`（app.py 组装开头，`opened.writable` 检查），根本到不了该行；EMPTY 库先完成迁移、`pipeline_runs` 表已存在，`list_ids()` 返回空即无操作；迁移失败同样先于该行抛出。启动用例（全仓 854 passed）无回归。
3. **新测试断言真实钉住终态、shutdown 不掩盖失败**：两条 worker 用例在断言"无 runCrashed + runFinished 终态 + **独立新连接**回读 `pipeline_runs.status` 一致"之后才调用 `controller.shutdown()`；且 `runFinished` 信号本身在 `_on_finished` 内部 `shutdown()`（quit+wait）之后才发出，故断言执行时 worker 已 join、最后一次 `_persist` 已提交——DB 回读断言不可能被并发写掩盖。AC③ 用例直接改 `status` 列 + `run_json` 模拟崩溃残留、经重新装配后独立连接回读，忠实且不依赖被测对象自证。
4. **P0/P1 排查**：无数据损坏风险（§3-1）；无新增吞异常/静默失败（`_Worker.execute` 的 `except Exception` 为 TASK-013 既有代码，本切片消除的是其触发主因，未新增 except）；无白名单外改动（§1）。**未发现 P0/P1**。
