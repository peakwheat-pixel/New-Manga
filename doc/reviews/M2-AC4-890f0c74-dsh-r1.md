## 5. 对 xfail 手法的裁定

**裁定：接受，但集成记录必须显式披露并承接（approved_with_conditions 的条件之一）；不建议改为显式 FAIL 记录并移出默认套件。**

支持接受（verified-by-reading）：
1. `Task:62` 明确要求「发现缺陷时如实记录 FAIL/BLOCKED 证据并停在该场景」，未禁止 xfail；纯验收 Task 把 FAIL 固化为**可复跑**的代码证据，强于只在 Markdown 里写 FAIL。
2. `strict=True`（`test:546`、`:751`）使缺陷一旦修复必然 XPASS 报错 —— 这是真实存在的防腐机制，Owner 在 `Task:85`、`verification-results.md:55`、`Handoff:39/67` 三处说明。
3. 披露充分、无「洗绿」：`test:30-35` 的模块 docstring 明写「they encode ACCEPTANCE verdict FAIL evidence」；`Task:49/50/52`、`verification-results.md:30/34/38`、`Handoff:27-31` 全部标注 XFAIL = FAIL 证据。
4. xfail ≠ skip：skip 会永久静默，strict xfail 在意外通过时变红。

反对派合理内核（必须在集成记录承接）：
1. xfail 的断言对象是「缺陷存在」，把缺陷固化为默认套件的「期望状态」，与仓库既有纪律相悖（`verification/M2-AC2/review-dsh-import/dsh-m2ac2-review-result.md:9` 以「全文无 skip/xfail」为纪律证据；`verification/TASK-041/…:26`、`TASK-044/…:27`、`TASK-062/README.md:40` 均以「无新增 skip/xfail」为核对项）。本 Task 是仓库首个引入 xfail 的验收套件（grep `tests/**` 仅本文件有 xfail）。
2. **修复即红的死锁**：F-1/F-2 修复后默认套件变红，而修复 Task 的范围通常不含 `tests/m2_acceptance/**`。
3. xfail 不区分失败原因：修复后若该测试因环境原因失败，仍显示 xfailed，掩盖 XPASS 信号（对应 P3-3）。

条件（P1/P2 关闭时必须一并落实）：
1. 集成记录逐条登记「2 个 strict xfail = 已确认缺陷 F-1/F-2 的验收证据」，并写明「默认 `tests/m2_acceptance` 从此长期为 32 passed + 2 xfailed，非全绿是已知受控状态；不得据此把新增 xfail 正常化」。
2. F-1/F-2 修复 Task 的**允许修改范围必须显式包含** `tests/m2_acceptance/test_reader_export_lineage_library_pagecount.py` 中对应 `@pytest.mark.xfail` 的移除与断言转 PASS，并把「XPASS 出现即处理」写入其验收标准。
3. 建议（非阻断）：在 xfail `reason` 中写明预期失败点（断言/行号），并补一份 `--runxfail` 的真实 traceback，证明失败原因就是 F-1/F-2 而非环境（P3-3）。
4. 不建议移出默认套件：移出后该证据不再被 CI 执行，防腐能力下降；也不建议改成「显式红测试」——那会让默认套件常态红，比固定 2 xfailed 更糟。
