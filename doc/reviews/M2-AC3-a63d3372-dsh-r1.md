## 判别力意见（对 M1/M2 先红记录的独立评估）

**判定：两段先红记录可信，机制与行号自洽；但覆盖面各有明确边界，建议补两类 mutation。**

- **M1（`_aggregate_run` 吞 FAILED）**：命中点唯一（全文件通读，`service.py:989` 是唯一 `elif PipelineTaskStatus.FAILED in statuses:`；`:1010` 是 `if`，不被 sed 命中），无"变异未生效"风险。变异后 `statuses` 全为终态，代码必然落到 `service.py:991-994` 的 `else` 分支并把 run 置 `COMPLETED`，因此 test:404 必然 AssertionError——记录的行号与机制完全自洽。
  边界：M1 只证"**run 级**聚合对 FAILED 敏感"，它是状态伪造里的弱形态（task 行仍如实为 FAILED）。真正把 `task.status` 伪造成 COMPLETED 的缺陷，M1 不覆盖；不过同一测试的 task 级断言（test:408、:481）独立承重，故判别力结论不受影响。
- **M2（step 级 typed code 塌缩为 generic）**：变异 `old` 块与 `service.py:713-717` 逐字一致（8 空格缩进、五行），带 `count(old) == 1` 守卫；`new` 只改 `step_run.error_code`，`task.error_code = code` 不变，所以 test:409（task 级）**应当通过**、test:413（step 级）**必然红**——记录的行号与机制自洽。该变异同时证明一个有价值的事实：套件的 step 级断言是**承重的**，若只断言 `task.error_code`，M2 类缺陷会被漏检。
  边界：M2 模拟的是"step 级单点塌缩"；生产中真正的塌缩路径是 `service.py:793-795` 的 `except Exception` → `_fail_step(..., "STEP_FAILED", ...)`，它同时污染 task 与 step 两侧。该真实路径由 test:409 + :413 双断言覆盖，但未被 mutation 直接证明。
- **建议补强（非返修项，可留后续 slice）**：① mutation `task.status = PipelineTaskStatus.COMPLETED`（task 级伪造）验证 task 侧断言；② mutation 走 `except Exception` 真实塌缩路径（例如让 fixture 抛非 `ProviderError` 的普通异常）验证双锚点同时变红。

**为什么整体不判 vacuous**：`-v` 日志的 8 个用例名与测试文件中的 8 个 `def test_` **逐一对应且顺序一致**（对比 `raw/pytest-provider-fail-closed-v.log:10-17` 与 test:239/292/333/375/449/523/573/618），日志与在审测试文件内容级吻合；套件内无任何 `try/except` 吞异常；AC3 的 A 页 `COMPLETED`（test:480）与 AC5 重试 `COMPLETED`（test:652）证明"同一装配下成功路径确实成功"，排除了"所有断言因一切皆失败而恒真"这一最危险的 vacuous 形态；断言均为顺序独立、无互相掩盖。
