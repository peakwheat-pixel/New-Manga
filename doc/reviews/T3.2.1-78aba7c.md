### 两项裁定（Handoff §Review 请求范围 2、3）

**1. AC3 在「本机模拟 + 宿主机装有 Python」局限下记 PASS：条件成立。**
理由：AC3 的实质是「包不依赖 Python/venv/源码/开发机 PATH 启动」。被测 launcher 的 PATH 已收缩为
`C:\WINDOWS\System32;C:\WINDOWS`，`python`/`py`/`git` 对子进程不可见，程序目录 ACL 为只读（reviewer 以
`icacls` 独立确认），数据根隔离到伪造 `%LOCALAPPDATA%`；更关键的是 reviewer 证明了**GUI 实跑所用的那个目录
与冻结清单逐字节相同**，因此截图 01–25 确属该固定包。用户裁决明确接受此路线并要求如实标注。
边界（必须随结论保留）：本机确实装有 Python，故「一台完全未装 Python 的机器」这一属性**未被证明**；
`icuuc.dll` 解析自宿主 System32，亦为宿主依赖。因此 AC3 只能读作
「**本机模拟条件下 PASS（PATH 受限、只读目录、隔离数据根）；干净机覆盖 = NOT_RUN**」，
且 D08 §53「干净 Windows 机器」与「全部 PASS 才可发布」的发布前置**仍然敞开**，不得据本 Gate 推断可发布。

**2. AC6 pipeline 以 fail-closed 诚实诊断记 PASS：不成立。**
理由分两层。契约层：reviewer 确认产品确实「无 mock 且绝不静默 mock」
（`runtime.py:10,239,432` 文档化；`_lazy_import` 抛 `ProviderDependencyMissing`；`probe_module` 报「module not installed」），
所以「诚实失败」是**正确的产品行为**——这正是 **AC5** 的要求，AC5 记 PASS **成立**。
但 AC6/D07 §106 把「Mock/Local Pipeline」列为主流程的一步，D08 §53 要求「全部 PASS 才可发布」，
故该步的**执行成功**是 AC6 的字面子项；产品既无 mock provider、权重又被排除，本 Gate 内不可能取得该证据。
结论：AC6 = **PARTIAL**（11/12 步骤 PASS，pipeline 步骤 = fail-closed 诊断）。
要转成 PASS 只有两条路，且都必须由用户/Codex 落笔：(a) 显式裁决「fail-closed 诊断即满足 AC-SMOKE 的 pipeline 步骤」；
(b) 另立子 Task 提供不依赖重型权重的 mock/local 路径。Reviewer 不代为推定。
