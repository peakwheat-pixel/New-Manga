## Architecture

**结论：可以合。** 选型（thread-local 槽位 + 可弱引用 lease 哨兵 + weakref 回调驱逐）是这类问题在 CPython 上唯一干净的解，三个"看起来能做其实不能做"的替代方案作者已用 spike 排除（`sqlite3.Connection` 不可弱引用、`_DummyThread` 死后仍留在 `threading.enumerate()`、QThread 死亡确实回收 local）。我独立验的三面：

1. **有界性是结构性的、引用计数级的**：修后 8 次真 run ⇒ registry 恒 1、打开连接 1；40 个顺序线程**不做任何 `gc.collect()`** ⇒ 峰值仍 1；4040 线程 churn ⇒ 峰值 1、0 异常。修前同尺子：[2,3,4,5,6,7,8,9] 与 9 条打开连接，3200 线程 ⇒ **1868 条打开连接**。R-002 的"句柄与 WAL reader 名额随 run 数单调增长"由此从推断变成计数。
2. **ident 复用互斥完备**：`_evict` 的两处删除都有身份守卫（`_connections.get(ident) is conn`；lease 槽只在 `() is None` 时删），`_current` 的 stale 分支先 `pop` 旧 lease 再覆盖 ⇒ 旧回调不会误删新线程的槽，被 pop 的 weakref 先死 ⇒ 闭包持有的旧连接随之释放。`_evict` 在锁外 close、`_current` 在锁内 close 同一对象的重叠窗口我按理论找过：唯一可能是"死线程的回调延迟到 ident 已被复用之后"，而 `close()` 幂等异常被 `sqlite3.Error` 吞（`ProgrammingError ⊂ Error`，我核过继承链），4040 线程 0 异常与之一致。
3. **文件系统守卫的顺序与覆盖面**：词法（原始 `split("/")`，`..`/`.`/空中段）→ resolve 后根包含 → **未解析路径逐级 lstat 拒 reparse**。顺序对了（reparse 检查跑在未解析路径上，正是 `resolve()` 会吞掉的那一层信息），且 `lstat` 失败即 `break`（不存在的级不可能被"穿过"）。合法删除路径两树都通过。成本我做了归因（M3）：**walk 每次删除多 6 个 `lstat`、约 73 µs，占整次 `remove_managed`（534 µs）的 14%**，其余是两次 `resolve()`（178 µs）与 unlink 本身——删除是 purge/sweep 级低频操作，可忽略；我不建议为省它加缓存。

**要收紧的是论断，不是代码**：`_evict` 的 docstring 写"此时无任何代码可再拿到该连接（闭包持有最后一个引用）"——闭包持有的是**连接**的最后引用*经由 facade 可达的路径*，但 worker 线程创建的 **cursor 对象、`with conn as c:` 绑定的真连接、`__getattr__` 返回的绑定方法**都可被别的线程持住。实测：修后一个被 GUI 持住的 worker cursor，在驱逐后 `fetchall()` ⇒ `ProgrammingError: Cannot operate on a currently closed database`（修前同一用例仍返回 1 行）。生产可达性我查了：全仓只有 `connection.py:162` 一处 `.cursor()`，无 `with conn as` 绑定 ⇒ **今天不可达**，故 R-003 记 P3 而非 P2。

## 四项重点答复（Handoff 指定）

1. **lease 回调的并发安全论证与 ident 复用互斥是否完备**：ident 复用/注册表突变这一半**完备**（上文 2，4040 线程 0 异常为证）；"无其他引用"这一半**过强**（R-003，实测反例是跨线程存活的 cursor）。修法建议收窄措辞并把"句柄不得跨线程存活"写成显式约束，而不是给 lease 加引用计数——后者要为不可达的场景付真成本。
2. **`any_in_transaction()` 能否支撑 TASK-057 前置①**：**语义方向对了，但它不是闸门，而且"no other writer"这三个字要改写。** 正面：M1 实测另一线程持 `BEGIN IMMEDIATE` + INSERT 时，GUI 侧 `any_in_transaction() is True` 而 `conn.in_transaction is False`——聚合确实看见了别人，R-004 的坑被这条方法绕开（作者用例名 `..._callers_own_transaction` 自陈只测了自己，见 R-005）。反面两条实测：(a) 门通过后 `RunController.start()` **仍可起新 run**（`run_controller.py:74-77` 只有"已有 run"闩，没有"已 shutdown"闩）⇒ 谓词是快照；(b) 一个**活着**的第二线程持可写连接时聚合为 False（registry=2、其自身 `in_transaction` False）⇒ "不 mid-transaction" ≠ "无写者"。真正承载保证的是 `shutdown() is True`（drained ⇒ run worker 已终止），而它今天成立还有一个谓词之外的事实：`RunController` 是**唯一**非 GUI 写线程（另一处 `threading.Thread` 在 `ui/viewmodels/export/viewmodel.py:291,344`，我读了 `application/export/**`，其唯一持久化是 `JsonHistoryDocumentStore`，不落 sqlite）。建议 TASK-057 的门写成三件：`shutdown() is True` + `not any_in_transaction()` + **"restore 期间不再接受 startRun"**（VM 侧闩），并把上面那句前提写进 docstring（R-004）。顺带：M2 实测"worker 带着半开事务死亡"⇒ 驱逐的 close 回滚之（独立连接读不到那行），这是归属模型的自然好处，值得留在 Task 里。
3. **reparse walk 覆盖面与每级 lstat 成本**：覆盖面**优于声明**——作者把"文件符号链接"列为 NOT_RUN（需开发者模式），本机 `mklink` 无参 **rc=0 可建**，我实测：修前该 ref 删掉的是链接的**目标**（受保护原件消失），修后 typed 拒绝且目标存活；另加两种作者未测形态（junction 建在 `books` 级、junction 指向根外）也全拒。成本见上文 3（73 µs/次）。唯一不满足 AC② 的是**作者用例自己的构造**：见 R-002。
4. **R-011 改真而非删除**：符合预期且**有后果**——修前 `"." in PurePosixPath(...).parts` 死条件不只是"看起来覆盖了"：我经**生产 trash 重试路径**喂一条 `revisions/./keep.png`，修前 `retry_pending_purges()` 返回 cleared=1 且文件消失，修后 typed 拒绝且存活。原始段判据还顺带覆盖了空中段（修前同样能删）。`PurePosixPath` import 一并移除，无死 import 残留。
