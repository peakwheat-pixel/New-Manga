## 两项登记事项裁决

### 裁决 ①：数据根默认 `%LOCALAPPDATA%/New Manga` —— **批准**

`default_data_root()`（`app.py:71-77`）的优先级为：`NEWMANGA_DATA_ROOT` 环境变量 → `%LOCALAPPDATA%/New Manga` → `Path.home()/New Manga`（`LOCALAPPDATA` 缺失时的回退）。另有 `--data-root` 命令行覆盖。

**批准理由**：①`%LOCALAPPDATA%` 是 Windows 桌面应用存放**本地（非漫游）用户数据**的正确位置，漫画库与托管图片体积大、不宜随漫游配置同步，用 `%APPDATA%` 反而不当；②存在环境变量与命令行两层覆盖，且 `--smoke-test`/`--screenshot` 一律走 `tempfile.TemporaryDirectory`，**探针模式不触真实用户数据**；③`LOCALAPPDATA` 缺失时回退 `Path.home()`，不会异常退出；④目录内再分 `library.db` 与 `managed/`，与 D03 §18 的根布局一致。

**建议（不阻塞）**：该默认目前只写在 `app.py` 的 docstring 中。请 Codex 在 D03 或 D07 中把它登记为正式约定（含"可用环境变量/命令行覆盖"），使后续切片与打包脚本有一处可引用的来源；正式的路径设置 UI 属 TASK-022。

### 裁决 ②：`app.py` 顶层 `QQuickWindow` 导入的必要性 —— **保留，但注释的因果表述需修正**

`app.py:35-38` 在模块顶层导入 `QQuickWindow`（`# noqa: F401`），注释称"引擎包装 `Main.qml` 的 `ApplicationWindow` 时，Python wrapper 类型取决于当时已导入的类型——没有它，`rootObjects()[0]` 会退化为不带 `grabWindow()` 的普通 `QWindow`"。

**裁决：保留该导入是合理且低风险的，但它并非 `grabWindow()` 可用性的必要条件。** 因为同一文件的 `_grab_and_quit()`（`:211-217`）在函数内**再次导入** `QQuickWindow`，并用 `shiboken6.Shiboken.wrapInstance(shiboken6.getCppPointer(window)[0], QQuickWindow)` **显式按目标类型重新包装**——即使顶层没有该导入、`window` 是 `QWindow` wrapper，这一次 rewrap 也会把它变成带 `grabWindow()` 的 `QQuickWindow`。换言之：`window.show()`（`:204`）与 `getCppPointer`（`:216`）在 `QWindow` wrapper 上同样可用，截图路径的正确性由 rewrap 保证，而不是由顶层导入保证。

**保留的理由**（故不建议删除）：①它让 `engine.rootObjects()[0]` 返回**强类型** `QQuickWindow`，使后续任何直接使用 `window` 的代码不必再 rewrap；②它把"wrapper 类型取决于导入时机"这一 PySide6 行为显式固化，避免未来移除 rewrap 时静默失效；③`# noqa: F401` 已表明作者知晓它是"仅为副作用而导入"。

**建议（不阻塞）**：把注释改为准确的双重保障表述——"确保 `rootObjects()[0]` 为强类型 `QQuickWindow`；下方 `_grab_and_quit` 的 `wrapInstance(..., QQuickWindow)` 是第二道保险"——或若决定改为只依赖 rewrap，则删除顶层导入并在 rewrap 处说明原因。**二者择一即可，属表述问题而非行为缺陷。**
