## 三轴结论

**Spec**：TASK-029 的 AC1～AC7 均有实现与测试对应。AC1 的 v1 冻结经逐字符比对确认**零改动**，v2 与设计 §3 逐条符合（含 F-02a 的状态值域与 F-02b 的 `DEFERRABLE INITIALLY DEFERRED`）；AC2/AC5/AC6 的"消费者契约不变、Tag 重复检查留在 Service、Pin 只改标志、恢复新增 Revision、reorder 产生 user Revision"均落实；AC4 的复合外键、唯一约束与"current 不可清空"触发器齐备；AC8 保持未勾选。**AC5 的"在 editing seam 中实现 `commit_region_revision`"在显式装配下成立，但默认构造路径不指向该实现（F-01）**，属实质缺口。

**Architecture**：分层方向正确——`infrastructure` 依赖 `application`/`domain` 的契约，Adapter 只做映射与事务，未把 SQLite 细节泄漏进应用层；`SqliteRegionRepository.update_region` 刻意只写软删元数据，把 revision-owned 状态收敛到唯一 seam，这是本切片最有价值的设计约束（有效阻止绕过 Revision commit 的写路径）；`add_revision` 明确"只做显式历史插入、不动指针"；`set_revision_pinned` 改为单语句 `UPDATE is_pinned`，修掉了 TASK-008 遗留的同 ID upsert。端口位置沿用消费侧定义（与 TASK-007/008 一致），TASK-028 已就此记录"暂不搬迁"的决策。需要修正的是默认 committer 的选择（F-01）与两处实现瑕疵（F-02）。

**Verification**：四条命令在**项目固定环境（Python 3.12.3）全部通过**（storage 33 / library 32 / editing 25 / 全量 96），与作者证据一致（仅全量数字记录有误，F-04）；在**系统 Python 3.14.6** 下 storage 与 editing 通过、library 9 项因缺 PySide6 失败（F-05），该差异如实记录且不计为实现缺陷。核心防线的测试强度可信：三类事务回滚（expected 过期、锁变化、DB 失败）与触发器/复合外键均有真实数据库断言；v1 冻结由结构断言 `test_v1_schema_is_unchanged` 与 Reviewer 的逐字符比对双重覆盖。**未运行项（并发、bootstrap 装配、损坏库恢复、性能）一律 NOT_RUN/N/A，未以推测代替。**

## 结论与复审

**`a2348e9` 暂不可交 Codex 集成：decision = changes_requested。**

阻塞项为 **F-01（P1）**：`RegionEditingService` 在未显式传入 `committer` 时会回退到 `InMemoryRegionCommitter`；该 committer 对 `SqliteRegionRepository` 只经 `update_region()` 落库，而后者按设计只写 `deleted_at`/`updated_at`，导致 **revision 入库但 `current_revision_id` 与 revision-owned 状态不更新**，同时调用方内存对象被改为"已提交"，形成无异常的静默不一致。**该缺陷已由 Reviewer 运行时探针实测确认**（DB current 两次均为 `None`、`geometry_json` 停留首次值、revision 行数正常增长，而内存视图显示已提交）。本 Task 所有 SQLite 测试都显式传 `committer=repo`，默认路径仅由内存 fake 覆盖，因此现有测试集无法发现该组合。修复成本低（优先采用 repository 自身的 `commit_region_revision`，或在未显式注入且 repository 具备该能力时抛错），并建议补一条覆盖该构造方式的测试。

F-02～F-05 为 P2，可与 F-01 同批处理或明确 de-scope：F-02 是异常边界与一行 no-op；F-03 建议在 Port 文档固定软删除读取语义；F-04 更正 96；F-05 建议对 Qt 依赖用例加 `importorskip`。
