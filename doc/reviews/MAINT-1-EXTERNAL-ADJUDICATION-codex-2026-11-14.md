## 裁决 A

**选择 1：手动拖拽排序。** 让用户已有的手动排序意图真正生效；章节号只是字符串，存在特别篇、空值、重复值与非数字编号，用它自动重排既不可靠，也可能打乱既有书籍顺序。暂不增加模式切换或废弃已有数据；相较方案 3，少一个持久配置与默认值迁移问题。

- 用户在书架的章节列表拖拽并持久化手动顺序；未设置 rank 的章节按原有 `sort_order` 排列。已有 rank 也必须生效；混合有/无 rank 时，有 rank 的章节在前，按 rank 升序，无 rank 的随后按 `sort_order` 升序；同 rank、同 `sort_order` 时以稳定章节 ID 作为最终 tie-break。首次拖拽以当前展示顺序为基准，为该书全部存活章节生成不重复 rank；不得覆盖其他书、删除的章节或其他元数据。新增章节默认排在手动列表末尾；撤销、失败和刷新后不能假装成功。
- **前提纠正**：当前代码中 `ChapterSummary` 已包含 `Kind` 和 `CustomRank`，Core 已在 `list_chapters` 输出二者；M2-C1 rev 2.16 已冻结该投影。见 `apps/desktop-avalonia/src/NewManga.CoreClient/CoreServiceClient.cs:38`、`src/bootstrap/core_service.py:4582`、`doc/contracts/M2-C1_TYPED_IPC_CONTRACT.md:18`。本裁决不需要扩 DTO。
- **契约边界**：现有 `list_chapters` 的 wire 返回顺序冻结为 `sort_order`，不能把 Core 返回顺序直接改为 rank 而宣称零 UNFREEZE。建议保持 wire 原样，在 UI/Host 的消费投影中排序；如果 DSH 要求改变 wire 顺序、提供批量原子重排命令或跨客户端一致顺序，须另行评估并经 DSH 授权相应 UNFREEZE，不在本裁决中预先批准。既有逐项写入是否能安全实现失败恢复及并发处理，须在冻结实施范围前核实；不能仅凭字段存在就断言零契约改动可交付。
- **开 1 张候选卡**：章节手动排序闭环，包含拖拽、持久化、重启回读、空值/重复/新增章节、失败及并发保护测试；DSH 先确认写入方案及是否需要契约载体，再冻结范围并释放。默认不改变阅读器的章节导航顺序；如果产品要求书架与阅读器共享顺序，应先明确消费端范围及冻结契约影响，不能静默扩展。

## 裁决 B

**选择 3：暂时保持现状，不为运行时重建或错误码拆分开实现卡。** 已有明确的重启提示，重启后可使配置生效；相较偶尔配置模型的用户收益，热重建会引入进行中任务、并发切换、资源回收和密钥生命周期风险，错误码 UNFREEZE 也有兼容成本。优先修复已有用户操作无可见效果的章节排序。

- 保留并清楚展示“修改模型配置后重启应用生效”；不要声称保存后已立即生效。现有行为是限制，不是热更新完成。若后续实测重启后仍不生效、提示不可见或用户无法完成配置，应单独按实际故障开卡，而非用本决定掩盖缺陷。
- 当前不引入新 wire 命令、不拆错误码，也不授权 UNFREEZE；三个原因仍可能显示同一个 `PROVIDER_NOT_CONFIGURED`。不得在尚未证明的情况下把它解释为某一种原因；诊断时避免暴露 API key 等敏感信息。
- 风险：用户需中断工作重启；排障区分度不足；已保存配置与运行中实例可能不一致。对于任务正在运行时的重启，应依现有恢复能力处理，不能假设任务必然安全恢复。收集实际发生频率和影响，若出现高频配置变更或恢复失败再由 DSH 重新排期。
