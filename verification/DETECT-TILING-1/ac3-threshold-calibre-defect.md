# AC3：阈值口径缺陷登记（RGBA vs RGB24）

**产出**: 2026-10-20 · **对应**: `DETECT-TILING-1` AC3
**要求**：登记缺陷并给出建议口径，**本 Task 明确禁止改常量值**。

## 一、缺陷陈述

`src/bootstrap/core_service.py`：

```python
#: ... (32 MiB RGB24 equivalent, see MAX_DETECT_PIXELS).
MAX_DETECT_PIXELS = MAX_DETECT_PAGE_BYTES // 3
```

**依据的假设是「解码后每像素 3 字节（RGB24）」。**

**而实测样本的 `mode` 是 `RGBA`（每像素 4 字节）。**

## 二、算术

| 口径 | `32 MiB` 对应像素上限 | 备注 |
|---|---:|---|
| RGB24（3 B/px） | **11,184,810** | **现行常量值** |
| RGBA（4 B/px） | **8,388,608** | RGBA 平面的正确上限 |

**反向核算**：一张**正好在现行上限**的页（11,184,810 px）

| 模式 | 满幅缓冲 | 与 32 MiB 的关系 |
|---|---:|---|
| RGB24 | 31.97 MB | **符合意图** |
| **RGBA** | **42.67 MB** | **超出 33%** |

**所以：现行常量在 RGBA 图像上放行了超过设计意图的页面。**

## 三、这是「收紧」不是「放宽」

**必须说清楚**：把上限从 11,184,810 降到 8,388,608 会**拒绝更多页**，不是更少。

**所以：**

- **修它不能让 `DETECT-TILING-1` 要解决的问题变好，反而会更严重**
- 一张 9 M px 的 RGBA 页现在会通过；修了口径后会被拒绝
- **`P18` 的 AC5「真实页像素超限」会因此多出一批被拒页**

**这是本 Task 禁止改常量的实际理由，不只是流程理由。**

## 四、但「不改」有代价，必须一并登记

**当前状态是：一个声明为「32 MiB」的保护，在 RGBA 图像上实际允许 42.7 MB。**

**这是保护与声明之间的不一致**，属于：
- **不是安全漏洞**（44 MB 仍然可控）
- **是契约不准确**——注释说 32 MiB，行为是 42.7 MB

**两条可能的口径修正方向**（需另立 Task 裁定）：

| 方向 | 做法 | 代价 |
|---|---|---|
| **A. 收紧常量** | `MAX_DETECT_PIXELS = 32 MiB // 4 = 8,388,608` | **拒绝更多页**；P18 缺口扩大 |
| **B. 按实际模式计算** | 先从 `Image.mode` 取每像素字节数，再算上限 | 需在检查前知道 mode（`Image.open` 后可读，**可行**）；行为随图像变化，更难预测 |
| **C. 只改注释** | 把「32 MiB RGB24 equivalent」改成准确描述 | **最小改动**，但保护实际上限仍是 42.7 MB |

**我倾向 B**，因为它让「32 MiB」这个声明真正成立，且不需要牺牲 RGB 图像的准入。

**但 B 有一个必须先验证的前提**：`Image.open()` 之后、`convert()` 之前，
`image.mode` 是否**总是可靠**（对 PNG 的 `RGBA` / `P` / `LA` 等模式，
`convert("RGB")` 之后每像素都是 3 字节，而满幅临时缓冲可能是 4 字节）。

**这一点本轮未验证，不应作为已定结论。**

## 五、一个必须记录的关联事实

**`SEC-FMT-005` 要求「检查可用物理内存」，而现行口径连「固定 32 MiB 对应多少像素」都不准确。**

**两者叠加的结果**：
- 阈值是固定的（不随机器变）
- 且固定的阈值算错了口径

**所以「内存保护」这一层目前有两个独立的缺陷，本 Task 只登记，不修。**
