# 阶段 2：候选解码路径实测与结论

**产出**: 2026-10-20 · **对应**: `DETECT-TILING-1` 阶段 2 的前置调研
**前置**：`stage1-decoder-memory.md` 已证明 `crop()` + `convert()` 不有界。

**本文件测五个候选方向，回答「有没有一条路能真正有界解码」。**

## 一、被样本的关键属性（本轮新发现）

```
format: PNG
size  : (690, 131289)
mode  : RGBA          <-- 注意是 RGBA，不是 RGB
tile  : 只有一个，extents = (0, 0, 690, 131289)   <-- 整图一个 tile
```

**两个决定性事实**：

1. **`mode` 是 `RGBA`**。满幅缓冲 = `690 × 131289 × 4 = 362.0 MB`。
   **这正好解释了阶段 1 测到的 `crop_1x1_convert` 峰值 324.4 MB**
   —— 接近满幅 RGBA 的大小。
2. **PNG 只有一个 tile，extents 覆盖整图**。
   **所以 Pillow 的 tile 接口在这张图上无法分块读取。**

## 二、五个候选的实测结果

样本：`690×131289 = 90,589,410 px`（RGBA）

| 候选 | 峰值增量 | 结论 |
|---|---:|---|
| **A. `Image.reduce(4)`** | **692.5 MB** | **更糟**——先整图解码再缩小 |
| **B. `Image.draft()`** | **0.0 MB** | **PNG 忽略 draft**（尺寸没变，仍 `690×131289`）|
| C. `numpy.fromfile` | 0.0 MB | 只读 1024 字节，**不解码**（不是解决方案）|
| **D. 流式读 PNG chunk** | **0.0 MB** | 能读到 `IDAT(len=56,182,321)`，**但不解码像素** |
| **E. `Image.tile` 低层接口** | 0.0 MB | **存在，但只有一个 tile 覆盖整图** |

**结论：五个候选全部失败。**

- A 反而更贵
- B 对 PNG 无效
- C/D 不解码，等于没做
- **E 是唯一看起来有希望的，但它对这张 PNG 退化成整图**

## 三、因此的结论

**在 Pillow 现有的解码路径下，没有一条能对这张 PNG 做有界分块解码。**

**原因不是 Pillow 实现得不好，是 PNG 这个格式本身的组织方式**
——**一张 PNG 是一个 zlib 流，必须从头解压才能得到后半部分的像素**
（除非扫描线级流式解码，而 Pillow 没暴露那个接口）。

## 四、剩下的真实选项（未测，需裁定）

| 选项 | 说明 | 代价 |
|---|---|---|
| **1. 换解码器（`pyvips` / `libvips`）** | libvips 支持**流式、分块、按需**解码，是这类问题的标准答案 | **新依赖**，需授权；且要验证它在 Windows + 本项目的 Python 3.14 上可装 |
| **2. 硬拒绝超限页** | 维持现状，但**给出准确错误与可操作建议**（如「请先降低分辨率」）| **不解问题**，但**诚实** |
| **3. 变更阈值口径** | 当前 `MAX_DETECT_PIXELS = 32 MiB ÷ 3`（**RGB24**），但实测解码常是 **RGBA（×4）** | 口径不一致是真实缺陷，**但改口径是收紧不是放宽** |
| **4. 先在导入侧转码** | 把超大 PNG 在导入时转成 tile 存储格式（如 TIFF tile）| 改变产品数据流，影响面大 |

**我倾向 1 或 2。但这是设计决策，应由 Codex 裁定。**

## 五、一个附带发现的真实缺陷

**阈值口径与实测解码模式不一致。**

`MAX_DETECT_PIXELS = MAX_DETECT_PAGE_BYTES // 3`，注释说「32 MiB RGB24 equivalent」。

**但实测这张图的 `mode` 是 `RGBA`（4 字节/像素），不是 RGB（3 字节）。**

**所以：**

| 口径 | 32 MiB 对应的像素上限 |
|---|---:|
| 按 RGB24（3 B/px） | **11,184,810** ← 现行阈值 |
| 按 RGBA（4 B/px） | **8,388,608** |

**即：一张 11 M px 的 RGBA 图，按现行阈值会被放行，
但它的满幅缓冲是 44.7 MB，超过「32 MiB」的设计意图。**

**这是一个真实的口径缺陷。**
**但它属于「收紧」而非「放宽」——修它会拒绝更多页，不是更少。**

**所以修它不能解决 `DETECT-TILING-1` 要解决的问题，反而会让问题更严重。**

**这与 `SEC-FMT-005` 的关系**：`SEC-FMT-005` 要求「检查可用物理内存，
分块或限制尺寸，给出清晰内存警告」。**若最终选方案 2（硬拒绝），
那恰好满足它 —— 但必须是「按真实解码模式」的拒绝，不是按 RGB24 推算的。**
