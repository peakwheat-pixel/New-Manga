## Decision and evidence basis

Project-level permanent deletion **requires a new IPC command**. Existing `LibraryService.delete_book` only sets soft-delete state (`src/application/library/service.py:85`); `TrashService.purge_batch` only purges a Page batch (`src/application/maintenance/trash.py:196`). The current Tauri production surface has no book-purge command. `library_control_run` controls Pipeline Runs and cannot delete a Book; `library_create_book`, navigation, and Page purge have incompatible semantics. No safe call sequence over the 58 existing Tauri commands can provide the required operation.

The prior P09 evidence confirms this is the sole uncovered AC3 path: the existing two isolated samples preserve their SHA-256 through import, soft delete, Page purge, `TRANSLATE_ALL`, `REINPAINT_REGION`, and `RERENDER_SINGLE`; project-level deletion is explicitly `BLOCKED` because the operation does not exist. Sources: [P09 blocked availability evidence](../P09/evidence/AC3-project-permanent-delete-availability.txt), [source hash matrix](../P09/evidence/AC3-source-hashes.json), [final workflow log](../P09/logs/37-ac3-workflow-source-hashes-final.txt).

At the baseline, M2-C1 is rev 2.8 / Core protocol 2.8. Tauri declares 51 production commands, 4 probe-only commands and 3 AC1-only commands (58 total), and `build.rs` documents the same counts. The main Tauri manifest, handler, capability and generated-permission surfaces are hand-synchronized; generated permission files carry `Automatically generated - DO NOT EDIT!`.

## Frozen IPC contract

The normative wire contract is [M2-C1 §5.11](../../doc/contracts/M2-C1_TYPED_IPC_CONTRACT.md#p09-ac3-delete-1-permanent-delete); this record pins the Task-local decision:

| Item | Frozen value |
|---|---|
| Tauri command | `library_delete_book_permanently`, production-only |
| Core command | `PermanentlyDeleteBook`, Core protocol major `2`, minor `9` |
| Invoke argument | `{payload: {book_id: BookId, confirm_permanent_delete: true}}` |
| Success | `{book_id: BookId, deleted: true}`; no paths or filesystem references |
| Scope | Exactly one active or soft-deleted Book ID; no path input, no batch array, no hidden soft-delete-to-purge sequence |
| Compatibility | Additive command and error-code strings; Core minor `2.8→2.9`; all existing 58 command requests, results, errors, enums and behavior remain unchanged |

The command does not reuse `delete_book` or `purge_batch`. `DeleteBook` in the M2-C1 command catalog remains a proposal and is not an alias for this operation. Missing/false/invalid confirmation and unknown payload fields map to `INVALID_REQUEST`; unknown Book to `BOOK_NOT_FOUND`; active or recoverable descendant Run/Task/Export operation to `BOOK_BUSY`; inconsistent/cross-Book relationship graph to `BOOK_DELETE_CONFLICT`; a failed DB transaction to `BOOK_DELETE_FAILED`; post-commit file cleanup failure to retryable `BOOK_DELETE_CLEANUP_PENDING`; unsupported protocol major to `PROTOCOL_VERSION_UNSUPPORTED`; an older same-major Core that does not recognize the additive command fails closed with `UNKNOWN`. A pending cleanup manifest is retried idempotently for the same `book_id`. ACL denial is rejected by Tauri before Core dispatch and produces no side effect. Core channel failure uses existing host-level `CORE_UNAVAILABLE`.

No existing global schema field or enum changes. The Core `ErrorEnvelope.code` remains a string; the new command adds its own code literals. A command-specific Tauri error projection exposes only `code`, `category`, and `retryable`, preserving the existing error DTOs for all other commands. Manual locks and current/pinned Revisions do not block the explicitly confirmed whole-Book delete; they are removed only with the complete project transaction. The UI must disclose this loss. Active/recoverable operations and inconsistent external relationships still fail closed.

## Data and resource semantics proposal

Book-owned relational data includes `books`; its `chapters` and `pages`; descendant `regions` / `region_revisions`; `media_artifacts` / `artifact_revisions`; page-linked `pipeline_run_targets`, `pipeline_tasks`, `step_runs`, `step_run_input_refs`, `step_run_output_refs`, `step_result_candidates`, `pipeline_stage_states`; `book_tags`; `reading_progress`; and `export_history` rows keyed by the Book or its Chapters. `tags`, global pipeline defaults, schema metadata, application metadata and global backup catalog rows are not Book-owned rows. The relation graph must be enumerated from the live schema and validated before mutation; unexpected external references fail closed.

The pending user decision on history retention is material: a no-project-residue delete would remove Book-linked Run/Task and ExportHistory rows, while a retained history would require a user-approved detached/scrubbed representation. No implementer may choose this policy. Page `source_hash`, artifact/region revision provenance and lineage records are part of project DB rows and are removed with those rows; the external P09 source-hash evidence and source pins remain in `verification/P09/evidence/**`. Any separate Audit/Provenance store discovered during implementation must be inventoried and brought to the user before removal or retention is selected.

Only Book-owned references within Managed/derived roots are eligible for reclamation: `pages.managed_original_ref`, `artifact_revisions.managed_path`, and catalogued derivative/cache outputs that can be authoritatively associated with the Book/Page/Revision. Every target path must pass root and reparse-point checks; no arbitrary recursive root deletion is allowed. Cleanup must be durable/retryable across a DB/file-system failure, and success is not returned until file cleanup and an orphan scan complete. User-selected export files outside managed roots are never reached by this command; whether a separate user-authorized export cleanup belongs in product scope remains undecided. Whole-database backups are outside this command's path authority; their retention/deletion boundary remains a user decision.

The user source directory is strictly separate. The request carries only opaque `book_id`; `source_filename` and `source_hash` are not filesystem authority. No source file may be moved, modified, or deleted. The purge may only reach Core-enumerated Managed Copy and derived resources under their guarded roots.

Locks and pinned/current Revisions must not be cleared or rewritten during preflight. The confirmed whole-Book operation includes them; they are removed only in the committed full-project deletion. A failure before commit leaves them intact. The confirmation UI must disclose the loss.
