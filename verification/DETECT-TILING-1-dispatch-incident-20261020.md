## 三、我判断的原因

**`DETECT-TILING-1` 的整包指令里同时包含**：

1. 5 条 AC（其中 AC1、AC2 各自都是开放设计问题）
2. 三条样本的尺寸与像素表
3. Pillow 自身 `MAX_IMAGE_PIXELS` 会先触发的约束
4. 四条禁止（不改阈值、不改 provider 契约、不调用方缩放、不复制素材）
5. 契约提醒（分块在 handler 层，不下沉到 provider）

**而 AC1 要求「先实测选定解码方式的峰值内存行为」，AC2 要求「设计跨 tile 去重策略」**
——**这两条都是需要决策的开放问题，不是执行步骤**。

**让一个 Agent 一次性完成「调研 + 设计 + 实现 + 实测 + 验证」，
它会在第一个开放问题上失去方向，而没有任何中间产出可验收。**

**这不是 `agy` 的缺陷。是我给的指令没有中间停靠点。**

## 四、拆分策略（下一轮执行）

**分四个阶段，每阶段一个可独立验收的产出：**

### 阶段 1：解码内存实测（只读 + 实验）

**目标**：回答「Pillow 在什么条件下会为超大图分配全图缓冲」。

**产出**：`verification/DETECT-TILING-1/decoder-memory-probe.md` + 实测数据。

**为什么先做这个**：AC1 的整个设计依赖它的答案。**而它不改产品代码，纯实验。**

### 阶段 2：设计定稿

**目标**：基于阶段 1 的实测，写出分块方案（tile 尺寸、重叠策略、去重规则、坐标映射）。

**产出**：`verification/DETECT-TILING-1/tiling-design.md`。

**为什么不交给实现方**：r34 要求 AC2 的去重策略必须写明选择与理由。
**这需要一个决定，而不是一个实现。**

### 阶段 3：实现

**目标**：按定稿设计写代码 + 测试。

**产出**：代码 + 测试 + Handoff。

### 阶段 4：验证与 Review

**目标**：真实样本实测 + DSH 独立 Review。
