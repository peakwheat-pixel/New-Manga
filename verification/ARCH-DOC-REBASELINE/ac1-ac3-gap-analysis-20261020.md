## 二、与前四项是同一性质

前面几轮查过 AC4 / AC5 / AC6：

| AC | 缺口 | 性质 |
|---|---|---|
| AC1 | Tauri IPC 编译校验、React 渲染验证 | **等实现任务** |
| AC2 | 跨进程集成测试套件 | **等 P09** |
| AC3 | React 视觉设计与交互原型 | **等 ZCode 设计 Gate** |
| AC4 | P18 的消费者实测 | **等 P18 重测** |
| AC5 | NFR 双环境实测 | **等第二台机器** |
| AC6 | `SEC-FMT-001~005` 与外部阅读器 | **等一个不存在的实现者** |
| AC7 | 固定 head 非作者 Review + 逐消费者 Gate 裁决 | **等消费者** |

**7 / 7 全部是「等下游」。**

## 三、这意味着什么

**`ARCH-DOC-REBASELINE` 是一个「Gate Task」——它的产出是规范与责任分配，
它的验收却依赖被分配方的执行结果。**

**这两件事在时间上必然错位**：

- 规范写完 = **它的工作完成了**
- 下游执行完 = **它的 AC 才能勾**

**而下游有 7 个不同的主体**（P09、P18、ZCode、消费者、第二台机器、不存在的实现者）。

**所以它永远不可能靠自己收口。**

## 四、这不是设计缺陷，是 AC 写法的问题

**Task 的《来源与目标》明确说它是 Gate**：

> 本任务是架构文档 Gate 的正式重基线：负责将既有产品需求与验收标准映射至
> 唯一演进目标架构 AD-001…

**「Gate」的验收标准，本该是「规范是否完备、责任是否分派清楚」**，
**而不是「被分派方是否已经交付」。**

**现在的 AC1–AC7 写成了后者。**

**举例**：AC1 要求「01–08 逐份核验，新技术架构/权限与 UI 映射具备正式来源」——
**这一句本身是「规范完备」的要求，而报告说它达成了**。

**但 AC1 的 `[ ]` 一直没勾，因为报告自己在 §5 里追加了一句
「Tauri IPC 编译校验与 React 渲染验证属于后续任务」——那是另一个要求。**

**AC1 里其实混了两个层次的东西**：

| 层次 | 内容 | 谁验收 |
|---|---|---|
| **Gate 层** | 映射与边界规则是否正式确立 | **本 Task 自己** |
| **消费层** | 实现是否遵循该映射 | **下游 Task** |

**而 AC1 的措辞把两层都包进去了。**

## 五、与前面两次「混写」是同一类

本 Session 已经遇到过两次「一条 AC 里混写多个判据」：

| 位置 | 混写的内容 |
|---|---|
| `P20-ISOLATION-1` AC4 | 绝对门槛（480 MB）+ 相对不回归（443.3 MB 基线）|

| **`ARCH-DOC-REBASELINE` AC1–AC7** | **Gate 层（规范完备）+ 消费层（实现验证）** |

**第三次，形态更严重**：前两次是「两个数字」，这次是「两个责任主体」。

## 六、因此的可执行建议（不由我裁定）

**方案 A：把每个 AC 拆成 Gate 层与消费层两行**

```
- [x] AC1-GATE：映射与边界规则正式确立（本 Task 可自证）
- [ ] AC1-CONSUMED：下游实现遵循该映射（由消费方 Gate 验收）
```

**这样 Gate 部分的完成度可见，消费部分的欠账也可见。**

**方案 B：另立「ARCH-DOC-REBASELINE-CONSUMPTION」Task 承接全部消费层验证**

**方案 C：维持现状**，接受本 Task 永远 `ready`，直到 7 个下游全部交付。

**我倾向 A**，因为它让「本 Task 做完了什么」变成可读的，
而 B 会制造一个同样永远等下游的 Task。

**但这是 Task 结构变更，应由 Codex 裁定。**
