## 1. AC1 诊断实证(根因:mtime 同 tick 碰撞 → 短路放过重写内容)

方法:临时诊断探针 `f02_diag_probe_loop`(已随交付移除),默认线程全 bin 运行,循环独立重放 f02 场景(首 fetch 200 → 等长原地重写 → 二 fetch),捕获首个非 400 时 dump:重写前后 `GetFileInformationByHandle` 原始 mtime(FILETIME,100ns)+ cache entry 的 `digest_verified`/`verified_mtime`(经 TEMP-DIAG 读取辅助,已随交付移除)。

**捕获率:3/3 次运行均捕获(round 5 / round 0 / round 2),每轮失败概率极高;无需降级路径。**

捕获 dump 原文(`raw/f02_diag_run1.log`,run2/run3 同构,mtime 值不同但 delta 恒为 0):

```text
F02-DIAG captured round=5 second_status=200 body=?+/;6w)3 ?w(?-(3.?w*;#65;>
F02-DIAG facts_before vol=1485189147 idx=2251799817143236 size=26 mtime=134350960517034742
F02-DIAG facts_after  vol=1485189147 idx=2251799817143236 size=26 mtime=134350960517034742
F02-DIAG mtime_equal=true mtime_delta_100ns=0
F02-DIAG entry(digest_verified,verified_mtime)=(Some((true, Some(134350960517034742))))
F02-DIAG: flaky failure captured at round 5 (see stderr dump)
```

根因判定(证据链):

1. 等长原地重写后,`identity_size_mtime` 读回的 LastWriteTime 与重写前**逐位相同**(`mtime_delta_100ns=0`),三连运行恒成立;
2. entry 状态 `digest_verified=true, verified_mtime=<同一值>` → `needs_digest=false` → digest 校验被短路 → 重写内容以 200 serve(`second_status=200`),即测试红时的 `left: 200 / right: 400`;
3. `vol`/`idx`(NTFS file index)/`size` 均不变,排除 identity/size 竞态,唯一通路是 mtime 比对;
4. 机理:NTFS LastWriteTime 的取值来自系统时钟,其推进粒度受系统定时器 tick 约束;fixture 写入与等长重写落在同一 tick 内即获得相同时间戳。**mtime 不是同 tick 等长改写的可靠检测信号,产品判定存在真实安全缺口**(非纯测试 flake):篡改窗口内的重写内容会被当作已验证内容 serve。

修复前基线(佐证间歇性):默认线程全量 `cargo test --bin m2rc1-desktop` 一轮,33 passed f02 绿(`raw/f02_baseline_run1.log`)——失败按 tick 边界概率出现,与 LISTBOOKS 集成时"三连首跑红"的高概率一致。
