# 阶段 1：Windows 内存 API 实测

**产出**: 2026-10-20 · **对应**: `DETECT-MEMORY-GUARD-1` AC1 的前置调研
**问题**：在设计一个依赖「可用物理内存」的准入规则之前，先确认这个 API 在本机返回什么，
以及那个数字是否承载 Task 假设的含义。

## 一、API 可用且稳定

`GlobalMemoryStatusEx`（`kernel32`），显式声明 `argtypes`，**调用成功**。

**本机三次连续读数**：

| 次 | 总物理内存 | 可用物理内存 | 负载 |
|---|---:|---:|---:|
| 1 | 31.6 GB | **8.7 GB** | 72% |
| 2 | 31.6 GB | **8.7 GB** | 72% |
| 3 | 31.6 GB | **8.8 GB** | 72% |

**三次波动 7.4 MB。**

**所以这个数字是稳定的、可用的**——不是那种每次都跳几十 MB 的不可靠指标。

## 二、关键发现：这个判据在正常机器上永不触发

**一张正好在 `MAX_DETECT_PIXELS`（11,184,810 px）上限的页需要**：

| 编码 | 满幅缓冲 |
|---|---:|
| RGB24 | **32.0 MB** |
| RGBA | **42.7 MB** |

**而本机可用物理内存是 8,700 MB。**

**42.7 MB ÷ 8,700 MB = 0.49%。**

**所以一个「可用内存是否足够处理这一页」的判据，在这台机器上永远不会触发。**

**只有可用内存低于约 43 MB 时才会拒绝——那时进程几乎已经在崩溃边缘，
这个保护也来不及做任何事。**

## 三、这意味着什么

**`SEC-FMT-005` 第 ① 项要求「内存管理器检查可用物理内存」。**

**技术上可以实现，且实现出来是正确的。**
**但在内存充足的机器上，它是死代码。**

**这不是拒绝实现的理由**——规则明确要求它，且它在极端场景（内存耗尽、
容器限制、其他进程占满）下确实有意义。

**但必须诚实记录**：

| 事实 | 含义 |
|---|---|
| 本机可用 8.7 GB，上限页需求 42.7 MB | **判据在此机器上永不触发** |
| 三次波动仅 7.4 MB | 数值稳定，可以做判据 |
| 只有可用内存 < 42.7 MB 才拒绝 | **那时机器已在崩溃边缘** |

**所以本 Task 的价值不在于「防止这台机器 OOM」**（它不会 OOM），
**而在于「规则完备性」与「极端环境下不至于无声崩溃」。**

## 四、AC2 的设计约束因此变清楚了

**AC2 要求「不得让可用内存成为唯一判据」。**

**现在有了具体数字支撑这条**：

- 若只用可用内存：本机永远放行（8.7 GB vs 42.7 MB），等于无限制
- 若同时用固定上限：固定上限（11.18 M px）才是真正的约束
- **两者组合后，实际生效的永远是固定上限，可用内存只是兜底**

**所以正确的组合方式是**：

```
拒绝 当且仅当：
  (页像素数 > MAX_DETECT_PIXELS)                      # 主判据，永远生效
  或 (页所需缓冲 > 可用物理内存 × 安全系数)            # 兜底，极端环境生效
```

**安全系数**需要一个值。**候选**：一个「不把机器吃光」的比例。

**这个值我不能自己定**——它是产品取舍（`SEC-FMT-005` 只说「适当」，没说多少）。
**应作为 AC2 的一部分由实施时给出理由，或提交裁定。**

## 五、一个必须记录的限制

**本 Task 的判据只在 Windows 上有效**（`GlobalMemoryStatusEx`）。
**若将来要跨平台，需要另行实现。**

**当前产品边界是 Windows 单平台**（`AD-001`），**所以这不是缺陷，是范围。**
