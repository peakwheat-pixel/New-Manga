# DETECT-TILING-1 阶段 2 方案裁定（r35）

日期：2026-10-20  
裁定者：Codex（Lead / Architect / Integrator）  
范围：仅裁定 `DETECT-TILING-1` 的技术方向、验收措辞及其 P18 / ARCH-DOC-REBASELINE 消费关系。本轮只新增本文件；不修改 Task、Plan、STATUS、代码、测试或既有证据，不调用 `coordinator-lease.py`，不执行 Git 写命令。

## 裁定摘要

1. **选择选项 2：维持 Pillow 与预解码拒绝，停止本 Task 的分块目标。** 不引入 `pyvips` / `libvips`，也不先做其 Windows + CPython 3.14 可行性验证。当前阶段 1/2 已否定 Pillow tile/crop 路径；换解码器会引入新依赖及运行时/打包验证面，须另有经批准的技术研究 Task 才能重新考虑。
2. `DETECT-TILING-1` 的目标应改为：**对超限页在触发像素解码前准确、安全地拒绝，给出可操作的尺寸/内存限制错误，并用实测证明拒绝路径没有触发整图像素分配；不再承诺超限页可检测。** 这是保守的产品行为，不是分块验收。
3. 将 AC1 改为本文件 §2 的“预解码安全拒绝与内存证据”；**删除 AC2**。既然不产生 tiles，就没有跨 tile 去重/ownership 可验收对象。
4. `SEC-FMT-005` 明文允许“分块处理或适当限制最大处理尺寸”，因此**分块不是强制实现**。但当前代码的像素上限和通用错误尚不能单独证明 SEC-FMT-005 全部满足：仍须把可用物理内存检查/明确上限、超限前拒绝、用户可读警告和 OOM 防护逐项映射并提供证据。该安全验收继续留在收窄后的 Task 范围内。
5. `MAX_DETECT_PIXELS` 当前以 RGB24 计算，而真实 PNG 可为 RGBA；32 MiB ÷ 4 = **8,388,608 px** 是 RGBA 原始像素平面的对应上限。此缺陷成立，但 `DETECT-TILING-1` AC3 明确禁止改常量值。本次不授权直接改值；正式重写 Task 时应把“准确拒绝”与阈值口径修正一并纳入冻结范围，或先另行裁定 AC3。不能继续把当前 11,184,810 px 称作覆盖 RGBA 的 32 MiB 上限。
6. **P18 保持 `closed_with_limitations`，其 AC5 的真实页像素超限继续为 limitation/未通过。** `ARCH-DOC-REBASELINE` AC4 的消费者实测也保持 `PARTIAL`；若该 Task 后续经授权以 limitation 收口，应同步记录同一消费者限制，不得将“安全拒绝成功”写成 P18 质量链通过。当前文件本身不更改任何权威状态。

## 1. 依据与范围边界

阶段 1 使用三个样本、六种访问模式、独立子进程和显式 ctypes 签名测 Working Set。决定性结果是最大样本 `690×131289` 上，`crop_1x1_convert` 的峰值增量为 **324.4 MB**；`Image.open` 的像素解码保持惰性，但像素访问会触发整图解码。因此 Pillow `crop()` 后逐 tile `convert()` 不构成有界解码证明。

阶段 2 的最大 PNG 样本为 RGBA，只有一个覆盖整图的 Pillow tile。`Image.reduce(4)` 实测 **692.5 MB**；PNG 忽略 `draft()`；文件读取和 chunk 探测未解码像素；低层 `Image.tile` 仍只有整图 tile。阶段 2 由此确认：该 PNG 的 IDAT 是一个 zlib 流，不能靠切分 Pillow tile 获得所需的局部解码界限。这些实验否定了本 Task 原定的 Pillow 分块路径，但没有证明所有替代解码器不可行。

当前 `handle_detect` 在 `Image.open` 后校验格式和像素数，在超过 `MAX_DETECT_PIXELS` 时抛出 `DetectRequestError`，随后才执行 `image.convert("RGB")` 和 `rgb.tobytes()`。所以现有代码对超限输入已有**预解码拒绝的基本形态**；当前错误仅说明 pixel limit，且上限注释按 RGB24 表述，不能据此宣称 RGBA 源内存符合 32 MiB，也不能推导符合 `SEC-FMT-005` 的可用物理内存检查和用户警告要求。

本裁定不释放实现、不改变 Task 状态、不修改任何阈值或 `ports.detection` 契约。`DETECT-TILING-1` 虽在当前 Plan / STATUS 标为 `ready`，但 r34 前置研究结果已改变实现前提；必须先正式重写 Task AC、范围和限制，再按协作协议冻结执行基线。

## 2. AC1 改写

建议以以下文本替换原 AC1：

> **AC1 — 超限输入的预解码安全拒绝与内存证据**：对 PNG/JPEG 请求，必须在任何触发像素解码或建立整页像素缓冲的操作之前完成格式、尺寸和资源策略判定。超过明确最大处理尺寸或内存策略的页面必须安全拒绝，错误应说明实际尺寸、适用上限及用户可采取的处理方式；不得通过 `crop()`、`reduce()`、`draft()` 或 Pillow tile 接口声称实现有界解码。对拒绝路径及允许处理的边界样本，在隔离子进程中记录峰值 Working Set、输入格式/色彩模式、尺寸、运行环境和调用顺序；证明超限路径没有发生像素解码/整页像素分配，且允许处理的输入受已说明的策略约束。该证据只证明本 Task 所测路径及样本，不得外推为所有 Pillow 编码的通用峰值公式。

AC1 的目标是验证**拒绝路径的资源界限与错误质量**，不再要求超限页面产生 region 或整页坐标，也不声称“实测已满足原有分块 AC”。“在 `Image.open` 后、像素读取前检查尺寸”与“记录拒绝前后的峰值”应作为实现和验证点；若某种格式的头部/元数据解析本身会触发像素分配，必须相应调整判定路径或拒绝声称满足 AC1。

## 3. AC2 与 AC3

### AC2：删除

原 AC2 的“边界去重、不漏检、tile ownership/overlap”整体删除，不改成条件式。当前选择的方案不产生 tiles，条件式 AC 会把未选方案的实现责任留在活动验收中。若未来批准替代解码器并重新选择分块实现，应由新 Task 按该解码器实际接口重建边界所有权和不漏检验收。

### AC3：不得沿用当前表述而不处理 RGBA 缺陷

现 AC3 禁止修改常量值，并冻结 32 MiB RGB24 等价语义；在裁定为预解码拒绝后，继续把 `11,184,810 px` 描述为适用于 RGBA 页的 32 MiB 上限是不准确的。按未压缩单平面计算，RGBA 的 32 MiB 对应 `8,388,608 px`。同时，解码器的临时缓冲/行缓存意味着这个算式只描述该像素平面，不是峰值 Working Set 上界。

因此，Task 重写时必须明确处理 AC3 冲突：要么经单独裁定允许把安全尺寸上限收紧到覆盖最宽源像素模式的值，并改写注释/验收语义；要么给不同模式定义准确限制并证明入口能够可靠判别。无论采用哪种，都不得放宽上限、不得把未压缩平面算式包装成解码峰值保证。当前授权仅允许产出本裁定，不允许在此直接改常量或 Task。

## 4. `SEC-FMT-005` 的映射

原文“分块处理或适当限制最大处理尺寸”明确给了替代路径，故本 Task 不必实现分块。但“限制尺寸”不是只保留一个像素阈值便自动合规。Task 验收至少应把以下事项逐项对照原文并留证：

- 明确允许处理的尺寸/资源上限及其适用色彩模式；上限与拒绝判断在像素解码/大分配前执行。
- 检查可用物理内存并说明它如何影响接受/拒绝策略；若固定尺寸限制也独立生效，应记录两项条件的优先级。
- 超限错误是调用方可读、可采取行动的警告，包含当前尺寸/限制及可行建议，不暴露无关内部异常。
- 对 `>10000×20000` 极端图像以及当前像素边界做负向验证，证明拒绝路径不解码并且不会 OOM；记录峰值内存和环境。
- 映射其它适用的格式约束与 `core.detect` 回归要求；不得将格式/base64/宽高一致性语义的变化夹带进来。

据此，原问“选项 2 是否意味着 SEC-FMT-005 已经满足”的裁定是：**规范允许此类方案，但现有证据不足以判定已满足；收窄后的 DETECT-TILING-1 仍需完成其安全限制与告警验收。** 若 Task 无法在其既有依赖与范围内实施物理内存检查，应先冻结为明确 limitation 并另立实现范围，不能在验收表中将整条 SEC-FMT-005 勾为通过。

## 5. P18 与 ARCH-DOC-REBASELINE 的收口

P18 AC5 记录的真实页为 `2946×4167 = 12,275,982 px`，高于当前 `11,184,810 px` 门槛，故 `core.detect` 在进入检测 provider 前拒绝它。r35 的方向不会降低此门槛或使该页可检测；更准确的错误和资源保护也不能代替 OCR/翻译/质量 pipeline 的真实运行。

因此：

1. P18 继续维持既有 `closed_with_limitations` 和 AC5 `BLOCKED` 事实。将“真实页因明确输入上限被安全拒绝，故本链未获得其检测及后续质量结果”记为长期限制，除非未来获批的新实现使该页可检测且 P18 依真实素材重跑通过。不能因 Task 2 的拒绝验收完成而重开或通过 P18。
2. `ARCH-DOC-REBASELINE` AC4 的映射/责任规范已完成部分与 P18 消费实测未完成部分继续分开；AC4 总体仍为 `PARTIAL`。若 ARCH-DOC-REBASELINE 经授权以 `closed_with_limitations` 结束，其 limitation 应指向 P18 仍未完成真实 JA/KO 消费实测，以及像素上限拒绝这项具体阻塞。不能把 AC4 改写为 `MET`，也不能只在 P18 留记录而让架构消费者链看似已闭合。
3. 当前裁定不执行上述 Task/Plan/STATUS 状态写入。它们须在后续获准的 Task 重写/closeout 中，以证据引用和明确生命周期决策分别登记；P18 与 ARCH AC4 不是同一个状态字段，不能互相替代。

这条链的技术重开条件是：一个经授权的新解码/检测实现能在安全资源策略内处理该真实页；随后重新执行 P18 所需的真实样本、模型/endpoint 与质量链，产生新证据。若产品决定长期保留硬限制，则两个消费者按各自生命周期保留 limitation，不再把“让超限页可检测”隐含成当前 Task 的目标。
