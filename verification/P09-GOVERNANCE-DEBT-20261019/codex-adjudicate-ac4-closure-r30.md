# P20 AC4 收口路径裁定（r30）

日期：2026-10-20  
裁定者：Codex（Lead / Architect / Integrator）  
对象：P20 AC4 判据、可测性及 P20 收口路径  
范围：只新增本裁定文件；未修改 Task、STATUS、Plan、代码或原始证据，未调用 `coordinator-lease.py`，未执行 Git 写命令。

## 裁定摘要

1. **交互延迟的统计口径不能由帧率裁决自动推出。** 2026-10-18 的 `avg ≤ 50 ms` 用户裁决，在 `fpsRecorder.ts` 和 `P20-AC4-FPS-1` 中明确指向帧时间 / 帧率部分。它没有说明交互延迟用 avg、p95 还是 max。故 20 个有效交互样本的 avg 36.0 ms 只能记为观测值，不能据此把交互延迟判为 `MET`；p95/max 62.4 ms 也不能在未约定 p95/max 是门槛时单独判 FAIL。交互延迟判据仍待用户明确，AC4 保持未达成。
2. **两处确属相近的 AC 缺陷模式**：多个统计量同时出现，但唯一判定统计量及优先级未预先写清。不过 AC4 当前问题不仅是 avg/p95 的选择；FPS 原文“稳定 60 FPS”与实现中的 avg frame-time ≤50 ms 也不等价。建议在协作规则中加一条窄而通用的可验收性规则，实施前通过治理 Task 修改；不在本授权下改 `doc/09_COLLABORATION.md`。
3. **当前没有证据支持“FPS MET”。** `FpsRecorderPanel` 虽已实现且可由 query/localStorage/build flag 显式启用，但产品代码没有挂载入口；CDP 不可用。原文 60 FPS 应按约 16.67 ms/帧理解，avg frame-time ≤50 ms 仅相当于平均不慢于 20 FPS，不能证明 60 FPS 或“稳定”。建议先开独立的测量入口/运行任务，再由用户确认与原 AC 相符的量化门槛；不应为 P20 收口临时扩大产品范围。
4. **撕裂采用限定的人工验收路径。** “无可见撕裂”没有直接 OS 自动化判据。可在明确操作脚本、设备/显示设置、观察者及记录方式后进行人工目视观察；记录为 `HUMAN_OBSERVED_PASS` 或 `HUMAN_OBSERVED_FAIL`，附带观察条件和证据。没有观察记录时仍为 `NOT_MEASURED`。若产品/环境不具备可靠观察条件，可由用户接受限制并记入 `closed_with_limitations`；不能把未测写成 PASS，也不建议以帧时间方差替代撕裂判断，因为它测量的是卡顿，不是画面撕裂。
5. **P20 现在不能转 `done`。** AC4 仍有判据未定、FPS 未测、撕裂未观察；且 P20 自身记录的其他子要求包括 AC1 干净环境安装/完整卸载、AC3 单图批处理峰值、AC5 本地模型 CPU 推理未实跑。应先补齐可执行的验收定义与证据，或由用户明确批准带限制关闭并保留每项原状态。`P20` 的 `canonical_evidence_status`、`resource_closeout_status` 当前均为 `pending`，Closeout Record 明确要求关闭时填写；转终态前必须按协议完成实际证据核验和资源核销。Plan 当前 `done: 42`；不能因本裁定改计数。若未来正式完成 P20 并满足全部关闭门槛，才按其正式终态更新 DAG 计数。
6. **可证的阻滞起点为 2026-10-18 首次留存的 P20 AC4 实测记录。** `STATUS` 与 P20 Task 表明当时已出现交互延迟数据、FPS/撕裂缺测，AC4 保持部分状态。现有材料不能证明“第几轮对话/执行轮次”或精确轮数，故不臆测。AC4 的测试方案没有在释放前确保每个子项均有可用测量路径和明确判据，这是**AC 设计/释放流程债**；执行侧在发现不可测后继续如实标 `NOT_MEASURED` 是正确处置，不是执行者造成缺口。后续将测量设施只实现为可选但无产品入口，也说明“实现测量器”与“验收可执行”之间缺少集成责任闭环。

## 1. 六项问题逐项裁定

### 1.1 交互延迟：avg / p95 / max

**本轮不把帧率的 avg 裁决外推给交互延迟。** 依据如下：

- `apps/desktop/frontend/src/perf/fpsRecorder.ts` 第 22–30 行将 avg ≤50 ms 明确称为 **frame-rate part of AC4** 的用户裁决，并始终报告 p95/max。它定义的是 `requestAnimationFrame` 帧间隔的判据，不是 UIA `Invoke → 后置条件可见` 的交互延迟。
- `doc/tasks/P20-AC4-FPS-1.md` 将 `avg ≤ 50 ms` 同样限定为 FPS 记录器的帧时间判据；该 Task 的设计范围没有给 UIA 交互延迟重新定义统计口径。
- AC4 原文“按键/点击交互延迟 ≤50 ms”没有统计量、分位数、样本数或首次操作是否纳入的定义。UIA 证据的 avg=36.0、p95=max=62.4，20/20 样本有效，说明不同统计量会得出不同结果；证据本身不能替需求方决定哪一项是门槛。

因此当前标签应为：**交互延迟判据 `UNRESOLVED`；实测统计量如实保留；不得按 avg 将子项标为 `MET`，也不得只按 p95 将其判为产品 FAIL。** 在完整 AC 口径确定之前，AC4 保持未勾选。建议用户在“avg、p95 或 max”中明确主判据，并说明首次切换样本是否纳入；该选择会改变既有结果，按 `doc/09_COLLABORATION.md` §4.4 的语义改动核验前置，应用前须核查其影响并保留现有基线，不得追溯改写数据。

### 1.2 与 P20-ISOLATION-1 缺陷是否同类；治理规则价值

**同类，但不完全相同。** 共同结构是：同一个 AC 的表达/记录出现多个可能用于判定的数值口径，却没有预先写明哪个是门槛、其他统计量如何处理。上一轮是绝对门槛与相对不回归的优先级不明；本轮是 avg/p95/max 的主判据不明。两者都可能导致不同执行者从同一证据给出相反结论。

建议增补的治理规则**有价值，负担可控**，但需要限定适用范围，避免要求每个简单 AC 都写统计学说明。推荐文字：

> **量化验收判据须唯一且可判定。** 当同一 AC 的数值门槛可能由多个统计量、窗口、基线或优先级解释时，AC 必须指定主判据、计算/采样方法及其他数值的用途（诊断、护栏或独立门槛）。未定义且会改变 PASS/FAIL 的，登记为 AC 可验收性缺陷；不得由执行者从观测结果反推门槛。若 AC 设计意图本就是多个独立门槛，则逐项列出，并要求全部满足或明示优先级。

此规则不应把 `avg/p95/max` 机械写入所有 AC；仅当多种统计口径会造成不同判定时触发。它与 §4.4 的关系是互补：本规则在 AC 起草/释放时防止语义空缺，§4.4 约束后续改变既有校验语义时先核验影响。当前授权只允许产出本裁定文件，因此建议另开 governance Task，由 Codex 按其生命周期修改协议并复核存量影响，不在本轮修改协作协议。

### 1.3 FPS 记录器：是否挂载、Task 归属与执行者

代码只读核验确认：`fpsRecorder.ts` 支持 `VITE_M2_FPS_SAMPLING=1`、`?m2_fps=1`、`m2rc1_fps_sampling=1` 三种显式启用方式；`FpsRecorderPanel.tsx` 有采样状态、统计和导出界面，但当前全仓没有产品模块导入它（只有测试导入）。所以“实现了记录器”不等于“当前 build 中已有可用的测量流程入口”。CDP 端点不可达进一步排除了无需挂载的外部驱动路径。

**裁定：**

- 不建议为 P20 AC4 临时加 Settings UI 或隐藏手势。它是新增的产品可达入口/维护面，不是只读测量；而且它只解决采样入口，不会自动解决 60 FPS 的统计判据和撕裂观察。
- 已有 query/localStorage 开关是否够用，须由测量 Task 在指定 build/启动方式下实际验证；不能把开关存在视为测量已可操作。若验证证明启动时确能启用、面板可操作并导出证据，可不新增 Settings 入口。否则应单独立“FPS 测量入口/运行器” Task，先冻结最小范围及是否仅测量构建，不并入 P20 closeout。
- 若需要 React UI/UX 改动，按仓库角色由 ZCode 主责；ZCode 无 headless CLI 时，按项目故障转移顺序派给 Antigravity，但新架构 React/Tauri UI/UX 仍由 ZCode 主责，故必须先在 Task 中明确授权 Antigravity 仅做必要的最小测量入口/工程接线，Codex 负责契约、范围及集成，DeepSeek Harness 可承担独立测量/Review。不能只因工具不可用就把实现自动派给非授权 Agent。

**60 FPS 判据特别说明：** 60 FPS 对应约 16.67 ms/帧。记录器注释中的 avg frame-time ≤50 ms 与此不等价。记录器可报告 avg/p95/max 并帮助分析，但在用户确认量化标准前，不应以它内置的 `avgWithinThreshold` 直接填 AC4 的“稳定 60 FPS”。

### 1.4 缩放平移撕裂：验收方式

撕裂属于呈现画面的帧级现象；帧时间方差/尖峰可暴露卡顿或不稳定，不是撕裂的等价自动化判据。当前证据说明没有 OS API 直接报告撕裂，且没有专用高速帧捕获设备。因此：

1. 推荐先用人工观察收口：冻结一份可重复操作脚本（连续缩放、平移、方向/时长）、显示刷新率与窗口条件；由未实现该功能的观察者在屏幕上检查是否出现横向断裂/画面不同步，记录 `PASS/FAIL`、观察者、时间、环境、操作、截图/录像（设备能力允许时）及限制。
2. 人工观察只覆盖该环境和该次操作，不宣称对所有硬件/刷新率或所有缩放路径普遍无撕裂。证据充分且观察通过，可将这一子要求记为**人工验证的 MET**；观察失败则留作未达成并开缺陷。
3. 若暂时无合格观察者/设备，就保留 `NOT_MEASURED`。只有用户明确接受这一限制并选择终止而不继续验收，才适用 `closed_with_limitations`；不改成 PASS。

人工验收是原文“无可见”最贴近的判据，但需明确“谁看、怎么操作、记录什么”。这不是把限制隐藏起来，而是将视觉判断从无法自动化的开放项转换为有边界、可复核的人类观察项。

### 1.5 P20 状态、Closeout Record 与 done 计数

当前 `doc/STATUS.md` 将 P20 列为 `ready`，AC4 为 `◐`；`doc/tasks/P20.md` frontmatter 为 `canonical_evidence_status: pending`、`resource_closeout_status: pending`、`integration_commit: null`、`delivery_head: null`。Closeout Record 明确含待填的关闭日期、两项 closeout 状态、删除/迁移/归档数量和未关闭项/保留原因。**因此 P20 确实有 closeout 字段，现状尚未满足终态流程。**

本轮不建议 `done`：AC4 仍未定义/未验证；此外 P20 正文与既有 r29 裁定仍记录 AC1 安装/卸载、AC3 批处理峰值、AC5 本地模型 CPU 推理的缺证。勾选符号不能代替所有子要求的证据核验。

本轮也不直接把它改为 `closed_with_limitations`。协作协议 §1 将此终态限定为**用户明确裁决**或已批准目标架构替代旧 Task，并要求保留未完成 AC/原状态与分类。本次要求的是 Codex 对收口路径作裁定，但没有明确授权放弃仍可执行的验收项。推荐当前仍保持 `ready`，暂不改 Plan 计数；由用户在完整限制清单和具体 closure evidence 可审阅后，选择继续补测或明确接受限制关闭。若用户选择限制关闭，按 §1 记录 AC4 与其他未测项的原状态，绝不改写成 PASS。若未来全部验收满足并完成 closeout，则可按 `done` 流程办理。Plan 现行 done 计数为 **42**，本裁定不改变它。

### 1.6 卡点起点、责任归属与重写文本

现有文件可支持的最早事实锚点是 **2026-10-18**：P20 交付记录已将 AC4 标为部分实测，列出延迟数据及 FPS/撕裂 `NOT_MEASURED`。它支持“至少自该轮记录起持续未闭合”，不支持精确的对话轮数/执行尝试数；不能把“第几轮”猜成某个数字。更早释放时是否有可行测量方案，须看该轮冻结的 Task/执行记录，当前指定证据不足以精确还原。

**债务归属：首要是 AC 设计与 Task 释放 Gate，其次是测量计划集成责任。** AC 把三个可观察性不同的要求塞入一项，却没有为 FPS 指定具体采样方法/判据，也没有为视觉撕裂指定人工观察协议；这使得释放时可验收性不足。执行者在无法验证时标注未测并保留未勾，是正确响应，不应归责为执行遗漏。治理流程可以通过释放前的“每个子要求均有方法、门槛、证据类型及执行责任”检查来预防。

在用户确认具体延迟口径和 FPS 稳定性定义前，建议将 AC4 拆成三项，避免 Codex 单方面重写产品门槛。可供用户裁决的候选文本如下（方括号内容须冻结后替换）：

> **AC4a 交互响应**——在指定 Windows 硬件/构建、预热状态和输入路径下，执行至少 20 次按键/点击并以“输入事件发出至指定 UI 后置条件可见”计时；包含 UIA 开销并逐样本保存原始数据。主判据为 **[用户裁决的 avg / p95 / max ≤ 50 ms]**；同时记录 avg、p95、max 与首次操作值。有效样本不足 20、计时边界不一致或记录缺失时不得判 PASS。
>
> **AC4b 单页/Webtoon 滚动流畅度**——在指定 build 与设备上，分别执行单页和 Webtoon 长图标准滚动脚本；使用可复核的逐帧时间采样，记录有效时长、样本数、avg、p95、max 及采样丢失。以 **[用户裁决的稳定 60 FPS 定义：例如 p95 frame interval ≤16.67 ms 且 max/超阈值帧比例有明确上限]** 判定；现有 avg frame-time ≤50 ms 不得单独作为 60 FPS 的等价证明。
>
> **AC4c 缩放/平移画面完整性**——按冻结的操作脚本、窗口/刷新率与显示条件，由指定的独立观察者进行人工观察；记录是否出现可见横向撕裂、观察者、环境、操作次数和带时间信息的影像证据（若可获得）。通过仅代表该测试环境与观察覆盖范围；无法执行时记 `BLOCKED/NOT_MEASURED`，不得推定通过。

此候选文本澄清测量对象与证据类型，但保留两个门槛供用户决定；在冻结前它不是实施授权，也不能用于回写本轮结果。鉴于既有 Task 范围/门槛变更涉及产品取舍，应另行记录用户裁决和 Task 范围后再执行。
