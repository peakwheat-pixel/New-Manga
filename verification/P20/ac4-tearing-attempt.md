# AC4 撕裂项：人工观察的尝试记录（未完成）

**执行**: 2026-10-20 · **结论**: **未能完成客观观察，撕裂维持 LIMITATION**

## 一、本轮的尝试

计划：启动 `m2rc1-desktop.exe`，在真实窗口里滚动/缩放，观察有无撕裂。

### 尝试 1 — PowerShell `Start-Process`

启动后等待 8 秒，但命令在 300 秒时超时转后台，**后台 job 随后被回收，应用进程一并消失**。
复查 `Get-Process -Name m2rc1-desktop`：**无进程**。

### 尝试 2 — CUA 桌面工具

- `get_desktop_state`：成功截屏 1920×1080，**但画面上是 Edge 的抖音页面**，
  应用窗口不在前台，也未被列出。
- `list_windows` / `launch_app`：均报 `this session has ended; call start_session explicitly`。
- `start_session` 返回成功，**但紧接着的下一次调用又报同一错误**。

**CUA session 在本环境下不稳定，无法完成「启动 → 操作 → 观察」的序列。**

### 尝试 3 — PowerShell 枚举窗口

确认当时只有 Edge、Clash、DSH、微信等窗口，**没有 `m2rc1-desktop`**。

## 二、因此本次**没有**观察撕裂

明确记录：**本轮没有看到应用窗口，也没有执行任何滚动或缩放操作。**

**所以不能声称「已验证无撕裂」，也不能声称「观察到撕裂」。**
**撕裂的判定状态维持 `UNOBSERVED`。**

## 三、为什么这一项本来就难以客观化

撕裂（tearing）是**帧级呈现现象**：GPU 在显示器刷新中途扫描出半新半旧的画面。

**Windows 上没有任何 API 报告它**：

- `DwmGetCompositionTimingInfo` 只给合成时序，不判定撕裂；
- ETW 的 Present 事件给呈现时刻，但不告诉你扫描线是否撕裂；
- 唯一可靠手段是**帧精确录屏**（高帧率采集 + 逐帧比对），或**人眼直视屏幕**。

**而本轮连「让应用窗口出现在屏幕上并保持前台」这一步都没做成。**

## 四、这一项的准确定性

**撕裂是 AC4 里唯一一个「验收手段本身未被建立」的子项**，另外三项不同：

| 子项 | 验收手段 | 状态 |
|---|---|---|
| 交互延迟 | UIA 端到端计时脚本 | **已建立并执行** |
| 帧率 · 单页 | `fpsRecorder` + 真实桌面滚动 | **已建立并执行**（1266 样本）|
| 帧率 · Webtoon | 同上 | **已建立并执行**（1202 样本）|
| **撕裂** | **无自动化手段；人工观察亦未完成** | **未建立** |

**所以它不是「测了但没过」，也不是「没测」，而是「没有可执行的验收程序」。**

## 五、建议（供裁定）

三条路，各有代价：

1. **明确降级为 limitation 并关闭**：
   AC4 其余三项已实测 MET；撕裂以「Windows DWM 合成下撕裂极罕见 +
   本 Task 未建立帧精确采集手段」为由记 limitation。
   **代价**：AC4 的第三项从未被任何人验证过，包括人眼。

2. **由人执行一次并留证**：
   需要一台有显示器的真实桌面、一个人、一次滚动/缩放操作，
   以及一句「无可见撕裂」的书面确认（可附截图，但截图证明不了帧级）。
   **代价**：依赖人工，且证据强度天然弱于前三项。

3. **建立帧精确采集**：
   引入高速录屏（≥240 fps）与逐帧差异分析。
   **代价**：新工具链，工作量远超 AC4 剩余价值。

**交付方倾向第 1 或第 2 条，且认为第 3 条不值得。**
**但这是验收标准问题，应由 Codex 裁定，若涉及产品取舍则由用户决定。**
