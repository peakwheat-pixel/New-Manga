## 2. P1 findings

### P1-1（阻塞）— `create` 的 `verified=true` 不是完整自检；缺失 managed 源文件时生成“自称通过但无法恢复”的包

证据：

- `create` 只做 DB read-back 检查：
  - `src/infrastructure/sqlite/nmbak.py:149-150`：`revision_refs = self._revision_refs()`；`managed_files = self._copy_managed_files(...)`。
  - `:171-180`：只校验重读的 `database_sha256` 与 `_package_database_matches`，随后把 `verified_manifest["verified"] = True`；**没有调用 `_verify_package`**，没有校验 `revision_refs` 的 managed 文件是否存在、sha 是否一致。
- `_copy_managed_files` 在源 managed 文件缺失时 **静默跳过**（`:326-345`），但 `revision_refs` 仍包含该条；`managed_file_count` 只统计已复制文件。
- `_verify_package`（`:393-439`）要求每条 `revision_refs` 的 managed 成员存在且 sha 匹配；因此 restore 会把 create 刚标记 verified 的包判为 `BACKUP_CORRUPT`。
- 独立探针（临时目录，未改动仓库）复现：
  - live DB 有 `rev-1` 指向 `books/.../page-1.png`，备份前删除该 managed 文件；
  - `create()` 返回 `verified=True`；
  - manifest：`revision_refs` 有 1 条、`managed_file_count=0`、zip 只有 `library.db`/sidecar/manifest；
  - `restore()` → `BACKUP_CORRUPT: missing managed file books/.../page-1.png`。
- 同一缺陷使 **pre_restore** 也可能生成“verified=true 但不可回滚”的包：若 live 库存在缺失的 current/pinned managed 文件，恢复前自动备份会先返回 verified，随后 restore 才失败，回滚点不可用。

影响：AC1 的“生成时读回自检、verified 语义”不成立；备份 UI 会收到“校验通过”的包，实际无法恢复。这是 blocker。

建议（按设计 §3.1 与 §3.3 二选一，但必须一致）：

1. create 在 `os.replace`/返回前调用完整 `_verify_package`（或等价校验：所有 refs 的 managed 成员 + sha + DB sha + 必需文件），失败则 `BACKUP_CREATE_FAILED`，不返回 verified；或
2. 若设计允许创建时缺失 current/pinned managed，则不要把这些 ref 放进 `revision_refs`，并在 manifest/返回中记录 missing，同时 restore 的 `_verify_package` 不再把包内缺失一律视为 CORRUPT，而是在恢复后由 consistency report 报 `BACKUP_RESTORE_INCOMPLETE`。
3. 增加“备份前删除一个 current/pinned managed 文件”的 create 回归测试；同时覆盖 `file_hash` 与源文件 sha 不一致的情况（当前 create 也会误报 verified）。

### P1-3（阻塞）— 恢复会写入 manifest 未列出的额外 managed 文件；`_verify_package` 不拒绝额外 managed 成员

证据：

- `_verify_package`（`nmbak.py:393-439`）只遍历 `manifest["revision_refs"]` 和可选的 `managed_files` 校验列出的成员；**不校验 zip 的 `managed/` 是否有多余文件**，也不校验 `managed_file_count`/`managed_total_bytes` 与实际是否一致。
- `_restore_managed`（`:467-478`）对解压后的 `managed/` 使用 `rglob("*")`，把 **所有文件** 写回 `self._managed_root`，而不是只写 manifest 列出的 managed_path。
- 因此，一个 DB/refs 校验通过、但额外加入 `managed/任意路径` 的 tampered 包会通过 `_verify_package`，restore 时覆盖/写入未列出的 managed 文件；这违背设计 §3.3“按 manifest 清单写入”，也使“损坏包在写任何东西前拒绝 CORRUPT”不完整。
- 现有测试只篡改 `library.db`（`tests/storage/test_nmbak_backup.py:187-200`），没有额外 managed 成员用例。

建议：restore 只写入 manifest 允许的 managed_path 集合；对 zip 中多余 `managed/` 成员直接判 `BACKUP_CORRUPT`（或明确忽略且记录），并增加“合法包 + 额外 managed 文件”测试。该问题与 P1-1 的“包内容不完整”是同一包完整性边界的两端。

### P1-4（阻塞，wire 契约）— `INVALID_REQUEST` 在 backup 面上被投影为 `internal`，与设计 §1 的 validation/non-retryable 不一致

证据：

- `src/bootstrap/core_service.py:274-281` 的 `_BACKUP_ERROR_RULES` 没有 `INVALID_REQUEST`。
- 备份 dispatch 对非对象 payload / 非法 backup_type 抛 `NmbakBackupError("INVALID_REQUEST", ...)`（`:3921-3934`），异常映射 `:3935-3937` 使用 `.get(code, ("internal", False))`，因此返回：
  - `code = INVALID_REQUEST`
  - `category = internal`（应为 `validation`）
  - `retryable = false`（值正确，但分类错误）
- 现有 `tests/core/test_core_backup_wire.py:178-187` 只断言 code，未断言 category；`test_tampered_package...` 对 `BACKUP_CORRUPT` 断言了 category，说明该契约本应被测试覆盖。

建议：把 `INVALID_REQUEST` 加入 `_BACKUP_ERROR_RULES`（`("validation", False)`），并断言 malformed create/restore payload 的 category/retryable；顺带为 `BACKUP_DELETE_FAILED`（当前也不在规则中）决定是否属设计允许的封闭错误码。
