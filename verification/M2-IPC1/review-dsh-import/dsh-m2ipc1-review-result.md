### P1

**P1-1｜seam §3 冻结的 shutdown 5s 超时→kill 未实现（Owner 可修，无新依赖）**
- 证据：`apps/desktop/src-tauri/src/library_bridge.rs:219-235`（Drop 内 `let _ = child.wait();`，`library_bridge.rs:233`），全文件唯一 wait，全仓 `timeout|kill` 无匹配；对照 `doc/tasks/M2-IPC1.md:37`「host 等待 5s，超时 kill」与 `verification/M2-IPC1/release-a54bb8c9.md:14`「实现偏离即违宪」。
- 影响：Core 在 shutdown 时挂死会让应用退出无限阻塞；AC2「超时行为符合 Seam 冻结」字面不成立。`Cargo.toml` 无 `wait-timeout` 类依赖，但可用 `try_wait()` 轮询 5s 后 `kill()+wait()` 实现，属无依赖修复。
- 修复建议：Drop 中发完 `core.shutdown` 后 5s 内轮询 `try_wait()`，超时 `child.kill()` 再 `wait()`；补一条 Rust 单测（可用一个不响应 shutdown 的假子进程 argv pin 验证 kill 路径）。

**P1-2｜扩生产命令面击穿 M2-RC2 / M2-AC1 的冻结 E2E 门，且 Handoff 声明「probe/ac1 零变化」**
- 证据链：`main.rs:35-41` 将 `PRODUCTION_COMMANDS` 由 3 条扩为 5 条 → 三模式 stderr 自报（`main.rs:334-338, 349-352, 362-365`）随之变化；而两个已 done Task 的 runner 做**精确等值**比对：`verification/M2-RC2/run_e2e.py:286-292`（production=3、probe=7）分别用于 `:400-404`（interactive production 面）与 `:428-433`（probe 自报，gate 键 `:554`）；`verification/M2-AC1/run_e2e.py:43-45`（6 条串）用于 `:240` 的 4 次 announcement 断言。本 head 上自报值变为 production 5 / probe 9 / ac1 8，上述门将全部 FAIL。
- 与 seam/文档冲突：`doc/tasks/M2-IPC1.md:44`（probe/ac1 模式面不得变化）与 `doc/handoffs/M2-IPC1-c4461c88.md:45`（probe/ac1 面保持零变化）未作限定或披露；被击穿的两个 runner 不在 Task 允许修改范围（`doc/tasks/M2-IPC1.md:57-62`），Owner 无法自行修复，需 Codex 裁决（更新两 runner 期望值，或明确 RC2/AC1 的 production 面定义随 IPC1 扩张而重定范围）。
- 附带：`main.rs:275-280` 在**所有模式**（含 probe/ac1）无条件 spawn 第二个 Python Core；而 M2-RC2 runner 只设 `M2RC1_*`/`M2RC2_*` 未设 `NEWMANGA_DATA_ROOT`（`verification/M2-RC2/run_e2e.py:217-224`），新 sidecar 会落到 `%LOCALAPPDATA%\New Manga`（`src/bootstrap/core_assembly.py:562-568`）并在真实数据根建库/迁移/`recover_running_runs`/legacy import——原本隔离的 E2E 不再隔离（可并为 P1-2 子项或单列 P2）。

## 是否达到可集成标准

**未达到，判定 changes_requested。** 理由不是产物质量整体不合格——Python envelope/命令面/装配顺序、SQL 聚合口径、DTO 安全边界、20 处路径的依赖方向、以及 Python 真实进程 e2e 判别力都达到了 Task 的 AC1/AC4 水准，AC5 的四条实跑证据与数字也自洽。阻断点是两处**硬约束偏离**：

1. seam §3 明文的「host 等待 5s，超时 kill」完全未实现（P1-1），而释放记录写明「实现偏离即违宪」，且该修复在 Owner 允许路径内、无需新依赖；
2. 扩生产命令面必然改变三模式自报串与 ACL 面（P1-2），已使 M2-RC2 与 M2-AC1 两个 frozen E2E 门在本 head 上必然 FAIL，而 Handoff「probe/ac1 面零变化」未限定、未披露，且修复涉及两 Task 的 verification 路径，必须由 Codex 裁决范围归属；此外 `main.rs:275-280` 无条件 spawn 的第二个 Core 让原本隔离的 RC2 E2E 写入真实 `%LOCALAPPDATA%\New Manga` 数据根，也应在同一裁决中处理。

**放行条件（建议）**：① Owner 以 `try_wait()` 轮询实现 5s→kill 并补 Rust 单测；② 修 `version` 非 dict 的 typed 拒绝（P2-1）与 `_fetch_page_counts` 的显式 typed 错误（P2-2，至少区分「查询失败」与「0 页」）；③ 补一条 Rust 真实 spawn `bootstrap.core_service` 的通道测试与一组 page_count 过滤判别用例（P2-3、P2-5）；④ 至少补一条挂载 `LibraryPanel` 且 client 拒绝的组件测试（P2-4）；⑤ Handoff 增补「跨 Task 影响」小节，如实记录 RC2/AC1 自报门变化、第二 sidecar 的无条件 spawn 与数据根后果；⑥ 由 Codex 明确更新 `verification/M2-RC2/run_e2e.py:286-292`、`verification/M2-AC1/run_e2e.py:43-45` 的期望值或在集成记录中裁定范围。P3 项按仓库惯例记录 disposition 即可，不阻断。
