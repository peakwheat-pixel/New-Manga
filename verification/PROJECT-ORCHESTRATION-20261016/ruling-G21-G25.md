- **日期**：2026-10-16。
- **权限边界说明**：按 [AGENTS.md](../../AGENTS.md)，**契约/任务分配/冲突决策属 Codex 职责**，**产品需求取舍属用户**。本裁决就"**是否授权契约修订、缺口如何处置、P15 的释放路径**"作出决定（可代理），并**把真正的产品取舍（v1 开放哪些分区）以"默认提案 + 可确认"的形式显式标注**，以免 P15 被无限期阻塞。

## 一、总裁决

**授权一个新的契约 Task `P15-C1`**，在 [P10 契约](../../doc/contracts/P10_CREDENTIAL_CONFIG_CONTRACT.md) 已确立的**逻辑边界**之上冻结设置面的 **IPC wire**，随后释放 **P15**（设置 UI）实现。

**理由**：G21–G24 的缺口性质完全一致——**语义已由 P10 冻结、缺的是 IPC wire**（设计原文对四者均写"契约 Task：冻结 X 面（P15 前置）"）。把它们**合并为一个契约 Task** 而不是四个，是因为它们同属"设置面"、共享同一 `settings_*` 通道与 Secret 边界，合并可避免四次往返与四个互相重叠的契约小节；**G25 例外**（见下）。

## 二、逐缺口裁决

| 缺口 | 处置 | 冻结内容与硬性边界 |
|---|---|---|
| **G21** Provider Profile 面 | **授权 `P15-C1` 冻结并实现** | Provider Profile CRUD、**Capability 默认绑定**、**绑定优先级解析展示**、**Run Snapshot 冻结查看**。依据 D04 §39–40 + P10 §5/§9。**多 Profile 同 Provider** 必须可表达 |
| **G22** 凭据操作面 | **授权 `P15-C1` 冻结并实现** | **专用一次性凭据操作**（新增/替换/清除）与 **`CredentialRef` exchange**；**只可读"已配置/缺失"状态**，**永不回显明文**；**普通 settings DTO 禁止承载 Secret**（沿 M2-C1 §5.3 与 P10 §3.4/§9）。**失败文案不得含原始响应/认证头** |
| **G23** Network Profile 面 | **授权 `P15-C1` 冻结并实现** | Network Profile CRUD + **分阶段连接测试**（Proxy→DNS→TCP→TLS→HTTP→Auth）：**未执行阶段必须明确标记**、**失败保留阶段**、**代理失败默认不得静默直连**；TLS 校验关闭须**危险确认且状态可见**。依据 D04 §41 + P10 §6 |
| **G24** 设置覆盖解析查询 | **授权 `P15-C1` 冻结并实现** | 解析**最终有效值 + 来源标注**（全局→作品→章节→当前任务）。依据 D04 §42 + P10 §5；**只读查询**，不得借它写设置 |
| **G25** 其余分区 schema | **部分授权 + 其余延期禁用**（**不整体授权**） | `settings_update_section` 按设计是**透传**（§5.3 不白名单化键集合）。**`P15-C1` 必须冻结一份显式的「P15 可编辑分区清单」**（每节的**键集与值域**），且**仅限**：(a) 已有 Core 写入校验实例或既有 handler 的节（如 `sfx.policy`）；(b) 由 P10 或既有契约**已确立语义**的节。**其余分区一律不在 P15 开放**，P15 中渲染为**禁用 + 原因"等待 section schema 冻结"**，并**逐节另立后续契约 Task**（符合 G25 原文"逐分区契约 Task"） |
| **G2** 回收站（**不属 G21–G25**，但属设计 §5.4 的禁用清单） | **本轮不授权**；P15 中**必须禁用** | 软删/恢复/永久删除/自动清理策略的 wire 未冻结；与 [BL-9](../../.orchestrator/BACKLOG.md)（"项目级永久删除"缺口）相邻，须由后续契约 Task 处理 |

## 三、产品取舍的显式标注（可确认，且不阻塞）

**哪些分区在 v1 可编辑属产品取舍**。为避免阻塞，本裁决采用**默认提案**，用户可随时覆盖：

- **P15 `P15-C1` 必须产出一份「可编辑分区清单」提案**（逐节：键集/值域/依据来源），并**优先纳入**已有 Core 语义、可端到端验证的节；
- **未列入清单的分区在 P15 中禁用**（可见分类 + 占位说明 + 原因），符合设计 §5.4 的 `disabled` 状态；
- **用户若要求扩大开放范围**，应为对应分区**另立逐节契约 Task**，不得在 P15 实现中"顺手"放宽键域。

## 四、释放路径

1. **立即释放 `P15-C1`**（kind=design/契约；Owner 建议 **Codex**）→ READY。
2. **`P15-C1` 关闭后释放 `P15`**（设置 UI；Owner 建议 **ZCode** 经 DSH `subagent_zcode` 派发——其 UI 主责资格已恢复；或 codex/antigravity）。
3. **P15 的禁用清单**必须至少覆盖：G2、未列入「可编辑分区清单」的全部节、以及任何 P15-C1 未冻结的能力。
4. `P15-C1` 不得改动 P10 已冻结的逻辑边界（只**新增** wire 与键域，不重开语义）。
