# `SEC-FMT-004` 的实测：功能达成，但机制与规范描述不同

**产出**: 2026-10-20 · **对应**: `SEC-FMT-IMPL-1` 的唯一待定项
**前一版留的**：
> 「无前缀添加」不等于「长路径一定失败」。
> 正确的下一步是：构造一个 >260 字符的路径，实测产品能否读取与转存。

**实测做了。结论是：能。**

## 一、用什么测的

**用产品自己的路径适配器 `ManagedFileStorage`**（`src/infrastructure/filesystem/managed_storage.py`），
**不是用裸 `pathlib`。**

**这很关键**：上一轮我用 `pathlib` 测了 345 字符路径，结论只能说明「Python 能」。
**这次测的是「这个项目的存储层能不能」。**

## 二、结果 1：`absolute_path` + 裸写读

| 场景 | 根目录长度 | 生成路径长度 | 结果 |
|---|---:|---:|---|
| short | 49 | 162 | **PASS** |
| over-260 | 302 | **415** | **PASS** |
| way-over | 417 | **530** | **PASS** |

**530 字符路径的写入与读回都成功。**

## 三、结果 2：完整生命周期（这才是决定性的）

**`ManagedFileStorage` 的全部路径操作，在根目录 303 字符、完整路径 434 字符下**：

| 步骤 | 结果 |
|---|---|
| `ensure_layout()` | **PASS** |
| `write_temp()` | **PASS** |
| `verify_temp()` | **PASS**（返回 `IntegrityInfo`，sha256 已算）|
| `publish()` | **PASS** |
| `os.path.exists()` | **PASS**（True）|
| 读回内容 | **PASS**（8192 字节）|
| `remove_managed()` | **PASS** |
| 删除后检查 | **PASS**（False）|

**7 / 7 全部通过。**

## 四、结论：`SEC-FMT-004` 的功能要求已满足

**原文**：

> 文件名含极端特殊 Unicode、空格或超长路径（**> 260 字符**）时，
> **路径适配器自动启用 Windows `\\?\` 长路径前缀**，
> **确保文件可被正确读取与转存**，地址栏不截断。

**拆成三项**：

| 要求 | 实测结果 |
|---|---|
| `> 260` 字符路径可读取与转存 | **满足**（434 字符完整生命周期 7/7）|
| 路径适配器**自动启用 `\\?\` 前缀** | **未实现，但不需要** |
| 地址栏不截断 | **未测**（UI 层，不在本探针范围）|

**所以：功能目的达成，但实现路径与规范描述的技术细节不同。**

## 五、为什么「不需要」是成立的，不是敷衍

**`SEC-FMT-004` 的措辞假设**：Windows 默认有 260 字符限制，所以必须加 `\\?\` 前缀。

**这个假设在 Python 3.6+ 上已经过时**：

- Windows 的 `CreateFileW` 等宽字符 API 一直支持长路径
- Python 3.6+ **在 Windows 上默认使用宽字符 API**
- 所以 `pathlib` / `open()` 本身就能处理长路径，**不需要 `\\?\`**

**`\\?\` 前缀仍然需要的场合**：

- 使用 ANSI 路径 API（`CreateFileA`）
- 未声明 `longPathAware` 且路径被 shell 或部分传统 API 处理
- 某些第三方库内部用 ANSI

**而本项目的存储层是纯 Python `pathlib`，所以不受这些限制。**

**这就是为什么「没有前缀添加」不等于「有缺陷」。**

## 六、但这不等于 `SEC-FMT-004` 可以完全划掉

**有三件事仍然值得做**：

### 6.1 地址栏不截断（未测）

**这是 UI 层的要求，本次未测。**

**若 UI 层显示路径时截断到 260，那是一个真实的用户可见缺陷，与存储层无关。**

### 6.2 显式测试（而不是靠本文件的探针）

**本文件是一个一次性脚本，不是回归测试。**

**若将来有人引入了 ANSI 路径 API 或第三方库，长路径能力会静默退化。**

**所以应该把这个探针转成测试。**

### 6.3 清单声明的价值

**虽然不需要 `\\?\`，但声明 `longPathAware` 会让整个进程（含第三方库）
在 Windows 上获得长路径能力。**

**这是纵深防御：即使某天引入了一个用 ANSI API 的库，进程级声明仍然覆盖它。**

**所以「加 `longPathAware`」是一个**成本低、收益明确**的改进——但它不是「修复缺陷」，
而是「把当前依赖的隐式行为变成显式保证」。**

## 七、最终判定

| 项 | 判定 |
|---|---|
| `SEC-FMT-004` 的功能要求 | **`MET`**（实测 7/7）|
| `SEC-FMT-004` 的实现方式 | **与规范描述不同**（无 `\\?\`，因不需要）|
| 地址栏不截断 | **未测**，可能仍是缺陷 |
| 回归保护 | **缺失**（只有一次性探针）|
| 纵深防御 | **缺失**（无 `longPathAware` 声明）|

**所以 `SEC-FMT-004` 记为 `MET`（功能），但附带两条建议**：

1. **把探针转成回归测试**
2. **加 `longPathAware` 声明作为纵深防御**

**这两条都不是「修复」，是「把当前的隐式保证变显式」。**
