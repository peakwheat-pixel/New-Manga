## 隔离身份与 profile

1. 采用 **LPAC（Less-Privileged AppContainer）**。主进程用 `STARTUPINFOEX` + `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` 创建，增加 `PROC_THREAD_ATTRIBUTE_ALL_APPLICATION_PACKAGES_POLICY=PROCESS_CREATION_ALL_APPLICATION_PACKAGES_OPT_OUT`。Profile capabilities 精确为空：不授 `internetClient`、`privateNetworkClientServer`、`registryRead`、`lpacCom` 或其他 capability。若程序需要其中任一权限，立即 `BLOCKED`，不得切换普通 AppContainer、追加 capability 或临时放宽 ACL。
2. 本次唯一 profile moniker：`NewManga-P02-LPAC-20261010-cddff584`（派生自本契约记录的主仓 HEAD；符合 Windows 允许字符与 64 字符上限）。只允许当前登录用户的一个 profile。开始创建前必须用只读 OS 查询确认其 profile、目录、SID 对应存储和私有注册表状态均不存在。任一部分已存在、归属不明或查验方法不能证明不存在，均停止且不得复用、覆盖或删除。
3. 仅由本次运行外部的非提权 Codex controller 调用 `CreateAppContainerProfile`。只有返回新建成功且得到 Package SID 才算由本次创建。`ERROR_ALREADY_EXISTS`、`E_ACCESSDENIED` 或其他 HRESULT 均停止；不得从 moniker 派生 SID 后继续复用现有 profile。
4. 用 `GetAppContainerFolderPath(PackageSID)` 得到当前用户该 profile 的真实 local-data 根；记录原始 API 返回路径、规范化路径、Package SID 及该目录与当前用户 `LocalAppData\Packages` 关系，并检查整段祖先无 reparse point / junction / hardlink 别名。该 API 返回值是唯一允许的 profile 路径来源；不得猜路径或写 `%LOCALAPPDATA%`、用户目录、通用 temp 根。
5. profile 内仅允许 LPAC Package SID 对 API 返回的唯一 profile local-data 根及其 `Temp` 子目录写入；`LOCALAPPDATA` 指向 API 返回值，`TEMP` 与 `TMP` 指向该根下 `Temp`。Profile 的私有注册表由 `CreateAppContainerProfile` 作为 profile 状态创建；运行进程不获 registry capability，故无注册表读写授权。外部 controller 通过 `GetAppContainerRegistryLocation` 只查询该当前 profile 的 HKEY 身份/状态，不写入。任一实际写入落到另一 profile/registry 路径即 `BLOCKED`。

## 子进程与句柄边界

- controller 运行在 LPAC 外，只执行 profile/ACL、hash、token/query、process/job/ETW 证据采集；不执行 repo/build 工具，不把用户文件句柄传入 LPAC。`CreateProcess` 的 `bInheritHandles=FALSE`，不使用继承句柄绕过路径 ACL。
- LPAC 主进程先以 suspended 状态创建，放入单一 Job Object 后才恢复执行。Job 设 kill-on-job-close 且不授予 breakaway；所有 `cmd.exe`、Python、PyInstaller hook worker、Node/npm、Cargo/rustc/linker 和任何后代必须留在同一 job、同一 LPAC Package SID 与 LPAC policy 中。
- 用 OS process-create/exit 事件及 Job Object 通知捕捉完整进程树，包括短命子进程；每个 PID + creation time 记录 parent PID、image canonical path/hash、`TokenIsAppContainer`、LPAC 标志、Package SID、user SID、integrity/elevation、capability SIDs、job membership 和启动/退出时刻。PID 复用按 creation time 区分。对无法捕捉、无法读取 token 或无法核对的进程一律判 `UNKNOWN` 并停止；不得只凭父进程身份推断子进程合格。若实际 P02 hook worker 无法满足此观测/继承边界，Build Gate 继续 BLOCKED。
- 首轮 isolation preflight 只运行无项目代码的 synthetic parent → child → grandchild token/cache/ACL probe。没有本契约审查、profile/ACL preflight、完整 process evidence 和 protected hashes 前，不运行 PyInstaller/Cargo/Tauri 或 P02 产品命令。

## Microsoft 一手资料（2026-10-10 核验）

- `CreateAppContainerProfile` 为当前用户建立 per-user/per-app profile 与文件夹/注册表存储；已存在时返回 `ERROR_ALREADY_EXISTS`，无创建权限时返回 `E_ACCESSDENIED`：[Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-createappcontainerprofile)。
- `GetAppContainerFolderPath` 返回该 SID 对应 profile 的 LocalAppData 路径；`GetAppContainerRegistryLocation` 返回当前 profile registry 的 HKEY：[folder API](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-getappcontainerfolderpath)、[registry API](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-getappcontainerregistrylocation)。
- `DeleteAppContainerProfile` 只接受 exact profile name；调用前应关闭 profile 中所有 handles，失败后状态不确定，需保留并报告，不能改用递归删除：[Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-deleteappcontainerprofile)。
- Microsoft 的 AppContainer 文档说明 LPAC 通过排除 `ALL_APPLICATION_PACKAGES` 收紧默认资源访问；network capability 缺失时不能访问网络；`LOCALAPPDATA`、`TEMP`、`TMP` 重定向到 profile；访问受 user/group SID 与 AppContainer SID ACL 双重限制：[Launch an AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer)。这些是 API 设计依据，不是本机已验证事实。
