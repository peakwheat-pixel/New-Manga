## 禁止项、分类和安全边界

本 Task 不调用 `CreateAppContainerProfile`、`DeleteAppContainerProfile`、任何 profile creation/deletion、private registry getter、registry write、ACL/owner/label 修改、permission canary、build/Cargo、AC1–AC7 或 Windows feature/Sandbox。绝不写 scratch、主仓其它路径、WER 目录、工具目录或用户数据。

分类含义：`PASS_WITH_EVIDENCE`=仅对应精确 getter/快照成功并留下输出；`FAILED`=查询异常、identity/target mismatch、ACL endpoint 变化或输入根/受保护哈希不可用；`UNPROVABLE`=未监测的访问闭包、TEMP/cache 到 scratch 的实际映射、有效 WER policy、缺失路径 ACL 等未被本 allowlist 证明；`REQUIRES_ACTIVE_TEST`=需后续受控 API/probe；`NOT_SAFE_FOR_R0`=仅历史阶段分类，R0 已结束，不阻止本 Task。单独分类 host-home 与 userprofile 一致性；即使该项 PASS，`tempCache` 仍 `UNPROVABLE`。PRESENT 目录的 owner 或 SDDL 为空时记录 `ACL_UNVERIFIABLE`；`hostAclSnapshots` 与 `hostPathSnapshots` 均不得标 PASS，前者=`UNPROVABLE`，后者=`UNPROVABLE`，并停止后续依赖步骤。`Get-Acl` 异常记录 `ACL_QUERY_ERROR`，保留此前已取得的 metadata、attributes 和 direct entry count；该异常使 `hostPathSnapshots` 与 `hostAclSnapshots`=`FAILED`。`Get-ChildItem` 异常保留已取得 metadata 并记录 `QUERY_ERROR`；若失败发生在读取 entry count 时，该 count 不可得。ACL endpoint 变化归 `FAILED`。仅当所有适用 ACL endpoint 都可核验、未变化且无 query error/unverifiable state 时，ACL 快照可 `PASS_WITH_EVIDENCE`；任一目标不存在而不可比较则 ACL 快照=`UNPROVABLE`。R1 不监测瞬时 ACL 变化或 OS access closure，始终保留 `UNPROVABLE_NOT_MONITORED_IN_R1`。Technical Gate 与 Owner waiver 分开记录，不能把 UNPROVABLE 改成 PASS。

任意身份/目标不符、scope 外过程/访问/写入、evidence 已存在、权限/API 错误、exception、hash不完整、证据写入失败：停止所有依赖对象，不重试、不修复、不清理。脚本只在目标 absent 时用 `FileMode.CreateNew` 写唯一 evidence；中断残留保持原样。
