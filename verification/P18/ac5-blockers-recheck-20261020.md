# P18 AC5 三项阻塞的复核实况（2026-10-20）

**背景**：`ARCH-DOC-REBASELINE` AC4 依赖 P18 消费者实测。
P18 以 `closed_with_limitations` 终止，AC5 被三项技术缺口阻塞。

**本轮复核这三项今天是否仍然存在。**

## 一、逐项核实结果

| # | 原阻塞 | 2026-10-20 实测 | 状态 |
|---|---|---|---|
| **1** | `ImportPages` = `UNKNOWN_COMMAND`（导入侧 wire 未实现）| `core_service.py` 有 `if command == "ImportPages":`；`library_bridge.rs:2789` 有 `round_trip`；`packaged_sidecar_tests.rs:278` 有断言 | **已解除** |
| **2** | `core.detect` 像素上限 `11,184,810 px` 拒绝真实页 `2946×4167 = 12,275,982 px` | `src/bootstrap/core_service.py:1410` 仍有 `"core.detect page exceeds the pixel limit "` | **仍存在** |
| **3** | KO detector 权重缺失（`PROVIDER_NOT_CONFIGURED`），`manga_ocr`/`paddleocr` 不可用 | `manga_ocr` **可导入**；`paddleocr` / `paddle` **仍缺失**；`weights/yolo26n.pt`（5.3 MB）存在 | **部分解除** |

## 二、因此我修正了一个判断

**本轮开头我按「推荐」判 P18 应重开**，理由是「AC2 已解除、只剩 AC5 技术缺口」。

**核实后这个理由不成立**：AC5 的三项缺口**只有第一项解除**，第二项仍在、第三项部分仍在。

**重开 P18 也跑不通完整链路**——即使 `ImportPages` 通了，
一张真实页 `2946×4167` 会先被 `core.detect` 的像素上限拒绝，
而韩文 OCR 的 `paddleocr` 仍不可装用。

**所以：重开 P18 不是「便宜的一次重测」，而是一项需要先解两个技术缺口的工程。**
**这与我在上一轮 `ac4-blocking-chain-20261020.md` §5 里写的「后者便宜得多」不符——那句话只对第一项成立。**

## 三、三项各自的性质不同

| # | 性质 | 解除成本 |
|---|---|---|
| 1 | **契约实现缺口** | **已解决**（`c219fe7` + `2ad590a31`）|
| 2 | **产品保护阈值** | **中**：像素上限是**有意的保护**（防 OOM），不是 bug。改它要么提高上限、要么加分块处理——**后者才是正确解法，但是产品改动** |
| 3 | **环境依赖缺失** | **中**：`manga_ocr` 已可用（ja 链路可走）；`paddleocr` 需安装，且**装不装得上取决于本机 Python 3.14 的 wheel 可用性** |

**第 2 项值得单独说明**：`11,184,810 px` 这个数字不是整数乘积的常见值。

**我一开始在上一版里写它是 `4096×2731` 反推的——那是错的，已核掉：**

```
4096 × 2731 = 11,186,176   ≠ 11,184,810
4096 × 2730 = 11,182,080   ≠ 11,184,810
3840 × 2912 = 11,182,080   ≠ 11,184,810
√11,184,810 ≈ 3344
```

**所以它不是一个按像素边长取的整数，来源目前未查明。**

**这不影响判断，但影响「能不能随便调它」**：
一个来源不明的阈值，**在不清楚它保护什么之前不应改动**。

**而 AC6 的 `SEC-FMT-005`（超大图 > 10000×20000）要求的恰好是同一件事**
——如何处理超限图像。**所以第 2 项和 `SEC-FMT-005` 是同一个技术问题的两面，
而分块处理（tiling）是同时满足两者的解法。**

## 四、因此 AC4 的结论不变

**`ARCH-DOC-REBASELINE` AC4 仍只能是 `PARTIAL`**，理由与 r33 一致：

> 已确认旧阻塞后来解除，但**没有修复后重跑的证据**。

**而现在可以加上更精确的一句话**：

> **即使想重跑，也跑不通全部三条**——`core.detect` 的像素上限会拒绝真实页，
> `paddleocr` 仍不可用。**AC5 的三项里只有一项真正解除了。**

## 五、给下一步的三个可执行项（按推荐优先级）

1. **`core.detect` 的分块处理**（tiling）——同时解决 AC5 阻塞 2 与 AC6 的 `SEC-FMT-005`。
   **一个改动解两个 AC。** 这是最值得做的。
2. **`paddleocr` 的安装可行性**——先确认本机 Python 3.14 有无可用 wheel；
   若没有，KO 链路在当前环境**客观不可跑**，应记为 limitation 而非继续等。
3. **P18 重开**——**在 1 和 2 之前没有意义**，会再次卡在同一处。

- 未安装 `paddleocr`。
- 未修改像素上限。
- 未重开 P18。
