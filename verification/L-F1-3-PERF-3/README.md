# L-F1-3-PERF-3：并发子项（第三次尝试）—— 结论：**在这台机器上无法有效测量**

基线 `9faf6e96f`。本卡试图解决 `L-F1-3-PERF-2` 指出的缓存污染问题。

## 1. 这次的设计（修正了上一轮的错）

上一轮的错误：4 线程读**同一个文件** ⇒ 页缓存复用。

本轮设计：
- 造 **8 个独立夹具**（各 123.7 MB，20 页 × 1200×1800 噪声 PNG）；
- **串行**用文件 `f0–f3`（运行前未被读过）；
- **并发**用**另外** 4 个文件 `f4–f7`（同样未被读过）；
- 两侧**总字节相同**（494.7 MB），**只有并发度不同**。

## 2. 测量结果

| 模式 | 总字节 | 墙钟 | 吞吐 | 每文件/每线程 |
|---|---|---|---|---|
| 串行（4 文件） | 494.7 MB | **0.35 s** | 1399 MB/s | 0.10 / 0.10 / 0.09 / 0.09 s |
| 并发（4 线程，各 1 文件） | 494.7 MB | **0.10 s** | 5039 MB/s | 0.10 / 0.10 / 0.09 / 0.09 s |

比值 **0.28x**（并发墙钟是串行的 28%）。

**重复一次**（此时两侧都已缓存）：串行 0.33 s、并发 0.10 s、比值 **0.30x** —— **与首次几乎一致**。

## 3. ★ 为什么这个数字仍然**不能**代表磁盘并发

**关键事实**：本机 **RAM = 31.6 GB**；全部夹具合计 **~1.6 GB**。

⇒ **所有文件在测量时都已经在操作系统页缓存里**（刚生成、且远小于内存）。

**证据**：并发时每个线程耗时（0.09–0.10 s）与串行时每个文件的耗时**完全相同** ——
若是真实磁盘 I/O 并行，4 个线程争抢同一块 NVMe 时单线程耗时应**上升**（带宽被分走），
而不是保持不变。

⇒ 本轮与上一轮测到的都是 **内存带宽 + CPU 并行**（4 线程约 3.3–3.6× 墙钟提速），
**不是磁盘并发扩展性**。

**在这台机器上无法有效测量冷磁盘并发**：需要 > 31.6 GB 的夹具才能压出页缓存，
而那样的夹具本身不可复现、也不适合放进任何测试。

## 4. 产品层面真正该问的问题（还没测）

对本产品而言，"并发吞吐"其实**不是**关键指标 —— 因为 **`_pipeGate` 是串行化设计**
（`CORE-PIPE-EXCLUSIVE-1`）：wire 层并发请求会被**刻意串行**，正是为了避免 E-6 那种响应错配。

**⇒ 正确的判据应该是**：
- 若 **wire 层并发吞吐 ≈ 串行** ⇒ **串行化生效**（符合设计，**不是缺陷**）；
- 若 **wire 层并发吞吐 > 串行** ⇒ **串行化失效**（**真缺陷**，会重现 E-6 类风险）。

**这个判据比"磁盘并发"重要得多，而它尚未测。**

## 5. 结论与对 `L-F1-3` 的最终口径

| 子项 | 状态 |
|---|---|
| 大文件 | ✅ 已测（1.3 GB / 1.74 s） |
| 占用文件锁 | ✅ 已测（typed `PermissionError`，fail-closed） |
| **并发** | ⚠️ **本机无法有效测冷磁盘**；且**真正该测的 wire 层串行化判据尚未测** |

**⇒ `L-F1-3` 仍不能判关闭。**

**建议口径**：「大文件与占用锁已测；并发在本机受页缓存限制无法有效测量，
建议改为测 wire 层串行化判据（吞吐≈串行即符合设计）」——
如 DSH 接受这个替代判据，`L-F1-3` 可在完成 wire 层测量后关闭；否则需换一台内存小于夹具的设备。

## 6. 我的第二次自我纠正（同一轮内）

第 `L-F1-3-PERF-2` 卡我说"要测并发就得避免缓存"，本轮**照做了**（换独立文件），
**结果仍然被缓存挡住** —— 因为我**没先确认夹具总量与 RAM 的关系**。

**这是第 9 次"先跑后想"。** 正确顺序应是：**先算夹具 vs RAM，再决定方案**。
