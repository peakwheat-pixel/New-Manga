# 端到端导出验证：产品真的产出可用文件

**产出**: 2026-10-20 · **探针**: 一次性脚本，结果 JSON 见 `e2e-export-probe-result.json`
**目的**：此前所有修复都在隔离层面验证。**这一次跑完整路径一次。**

## 一、做法

1. **生成 3 张 600×900 的纯色页**，每页叠一个**已知尺寸的黑色条**（400×40 = **16000 像素**）
2. **经 `ExportService` 真实导出** PDF 与 CBZ（不是直接调 composer）
3. **用从未见过本项目代码的实现打开**：PDF 用 PyMuPDF，CBZ 用 7-Zip
4. **读回像素，与写入的内容逐项比对**

**第 2 步是关键**：之前 `PDF-STREAM-FIX-1` 的测试是直接调 `_compose_pdf`。
**这次走的是产品入口。**

## 二、PDF 结果

| 页 | 尺寸 | 主导色 | 非白像素 | 黑像素 | 色数 |
|---|---|---|---|---:|---:|---:|
| 0 | 600×900 | **`(220,40,40)`** | 540,000 | **16,000** | 2 |
| 1 | 600×900 | **`(40,160,80)`** | 540,000 | **16,000** | 2 |
| 2 | 600×900 | **`(50,80,220)`** | 540,000 | **16,000** | 2 |

**逐项吻合**：

- **主导色** = 我写入的三种颜色，**逐页对应，无错位**
- **黑像素 = 16,000**，与我画的 400×40 条**完全相等**
- **色数 = 2**（底色 + 黑条），**不多不少**
- **`text_length: 0`**——纯图片页无文本层，**符合预期**（图片 PDF 不该有文本）
- **zlib 无报错**

**540,000 + 16,000 的关系需要说明**：900×600 = 540,000，**所以 `non_white` 等于整页像素数**——
因为底色不是白的。**16,000 是其中的黑色部分。**

## 四、这个验证覆盖了什么，没覆盖什么

### 覆盖了

- **`ExportService` → `QtFreePdfComposer` 的真实路径**
- **PDF 内容流的 zlib 完整性**（修复的实际效果，在产品入口上）
- **像素级正确性**：颜色、黑条位置与面积、色数
- **CBZ 的 ZIP 结构完整性**（CRC 校验）
- **`ComicInfo.xml` 的写入**

### 没有覆盖

| # | 未覆盖 |
|---|---|
| **V1** | **没有真实漫画页**——只有纯色 + 黑条。真实页的色彩分布与压缩比不同 |
| **V2** | **没有文本层**（`compose_searchable` 未走）——`text_length: 0` |
| **V3** | **没有桌面阅读器**——仍是独立实现，不是用户视角（承接 `SEC-FMT-IMPL-1` AC5 的 limitation） |
| **V4** | **没有大文件**（9542 字节 / 1163 字节）——未测 100 页、50MB 级 |
| **V5** | **没有并发或异常路径**（磁盘满、路径不可写） |

**V1 值得强调**：**纯色页是对压缩器最友好的输入**。
**真实页可能触发不同的压缩路径——虽然 zlib 的压缩路径不会改变格式合法性。**

## 五、与既有测试的关系

**既有的 `tests/export/test_pdf_stream_integrity.py` 有 4 个测试，覆盖**：

- 每个 `/FlateDecode` 流能解压
- `/Length` 与实际字节一致
- 渲染非白
- `compose_searchable` 也渲染

**本探针补的是它们没有的**：**走 `ExportService` 而不是直接调 composer。**

**所以这不是重复。但如果只跑测试，这个差别是看不出来的**——
**测试全绿时，产品入口是否通，是**另一个问题**。**

## 六、结论

**导出的 PDF 与 CBZ 都是可用文件。**

**不是「结构看起来对」——是像素与 CRC 都对。**
